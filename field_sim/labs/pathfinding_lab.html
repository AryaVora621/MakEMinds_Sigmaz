1. The map as a graph and a grid

A graph is a set of dots (nodes) joined by lines (edges). Think of a subway map: stations are nodes, tracks are edges.

Our field is 144 x 144 inches. We chop it into square cells. Each free cell is a node, and two neighbouring free cells are joined by an edge. In the lab, the cell size is 1, 2, 3 or 4 inches. With 2-inch cells the field has 72 x 72 = 5,184 cells.

The cost of an edge is how far the robot travels along it: 1 for a straight step, and sqrt(2), about 1.414, for a diagonal step. A path is a list of cells, each one next to the one before it, that never touches a blocked cell. The shortest path is the one with the smallest total cost.

Walls, the hive and the flowers are obstacles. A cell is hard (blocked) if the robot centre would come closer than 9 inches to an obstacle. Section 9 explains why 9.

2. Dijkstra: the cheapest way to every cell

Dijkstra's algorithm finds the cheapest cost from one starting cell to every other cell. The trick is simple: always finish the cell that is currently closest to the start. Keep the unfinished cells in a priority queue (a line where the smallest number comes out first).

dist[all] = infinity;  dist[start] = 0
push (0, start) into the queue
while the queue is not empty:
    (d, u) = pop the smallest entry
    if d is bigger than dist[u]: skip it     # old copy, already beaten
    for each free neighbour v of u:
        nd = d + cost(u, v)
        if nd is less than dist[v]:
            dist[v] = nd;  parent[v] = u;  push (nd, v)

Why it is correct. Suppose u has the smallest distance among all unfinished cells. Any other route to u has to leave the finished cells through some unfinished cell w. That cell is already at least as far as u, and every step adds a non-negative cost. So no other route can beat dist[u]. Dijkstra needs costs that are never negative. VERIFIED (Wikipedia, Dijkstra's algorithm)

Worked example: a 3 x 3 grid with no walls

Early exit. If you only need one target, stop as soon as the target is popped (not when it is first pushed). Then its cost is final.

3. A*: Dijkstra with a compass

A* works like Dijkstra, but it adds a guess of the distance still left to go. Each cell gets a score:

f = g + h
  • g = cost from the start to this cell (the same as Dijkstra's dist).
  • h = a guess of the cost from this cell to the goal. This is the heuristic.
  • f = the score. The queue always pops the smallest f.

If h is 0, A* is exactly Dijkstra. A good h points the search toward the goal and skips many useless cells.

Admissible means h never overestimates the true remaining cost. If h is admissible, the first time A* pops the goal, the path is optimal. VERIFIED (Wikipedia, A* search)

Consistent means h(u) is at most cost(u,v) + h(v) for every edge. A consistent h also means each cell is finished the first time it is popped, so the closed set can be trusted. VERIFIED (Wikipedia, A* search)

Tie-breaking. When two cells have the same f, our code prefers the one with the larger g, which has already travelled further. The idea is common practice and is meant to reduce work; its exact effect in our lab is UNVERIFIED until measured.

4. Choosing a heuristic for 4-way or 8-way moves

Let dx and dy be how far the cell is from the goal box along each axis (0 if it is already inside the box). Each guess is then multiplied by the cell size.

NameFormulaAdmissible for 8-way moves?Notes
zero0YesSame as Dijkstra. Safe but slow.
manhattandx + dyNoCounts a diagonal as 2 steps, but it costs 1.414. Fine only for 4-way moves.
euclidsqrt(dx^2 + dy^2)YesSafe, but weaker than octile.
chebyshevmax(dx, dy)YesTreats a diagonal as cost 1. Safe, but too low.
octilemax(dx,dy) + (sqrt(2) - 1) x min(dx,dy)YesExact on an empty 8-way grid. The strongest of these. Our default.

Why Manhattan fails with diagonals

Suppose the goal is one step right and one step up (dx = 1, dy = 1). Manhattan says 1 + 1 = 2. The true cost is one diagonal step, sqrt(2) = 1.414. Manhattan says 2, which is more than the truth, so it overestimates. An overestimate can make A* return a non-optimal path.

5. Why a diagonal costs sqrt(2)

A diagonal step crosses the corner of a 1 x 1 square. Pythagoras says that distance is sqrt(1 x 1 + 1 x 1) = sqrt(2), about 1.414. It is cheaper than two straight steps (cost 2), but more expensive than one (cost 1). Using real distances means the costs match the real world in inches.

Our rule also stops the robot from cutting a corner. A diagonal is allowed only if both cells beside it are free, so the path never squeezes between two blocked cells touching at a corner.

6. Weighted A*: faster, with a promise

Weighted A* multiplies the guess by a number w, which is at least 1:

f = g + w x h (w = 1 + epsilon)

A bigger w makes the search pull harder toward the goal. It expands fewer cells and finishes sooner. The price is a promise that is weaker than optimal:

If h is admissible, the path found has cost at most w times the best cost. With w = 2, the path is at most twice the shortest. VERIFIED (secondary sources; the exact wording differs between sources)

In the lab, the weight slider goes from 1 to 5. Weight 1 is plain A*. Our test suite checks the promise for w = 1.2, 1.5, 2 and 3. How much faster it is on our maps is UNVERIFIED until measured.

7. Theta*: paths that are not stuck to the grid

Grid paths zig-zag, because every move goes straight or diagonally. Theta* is a change to A*. When a cell's parent has a clear straight line of sight to a neighbour, Theta* connects them directly and skips the cells in between. The path can then cut across at any angle.

  • Pro: shorter and smoother paths.
  • Con: every step needs a line-of-sight check, so each expansion costs more.
  • Not guaranteed optimal. Basic Theta* can miss the true shortest path in continuous space. VERIFIED (research summary)

The lab's Theta* uses 8-way neighbours and the Euclidean guess. Our tests check that its paths are valid, not that they are the same length as A*.

8. Cost bands: near walls is expensive, not forbidden

Each cell has a soft multiplier of at least 1. It multiplies the cost of every edge that touches the cell.

  • Far from obstacles (distance 14 in or more): multiplier 1.
  • Between 9 and 14 in from an obstacle: the multiplier rises smoothly, up to 4 right at 9 in.
  • Closer than 9 in: the cell is hard and cannot be used.

The robot stays away from walls when it has a choice, but it can still pass through a narrow gap if there is no other way.

Why the heuristics stay admissible. Every multiplier is at least 1, so the real cost of a path is never less than its plain length in inches. The guesses in section 4 measure plain length, so they never overestimate. Our tests check this.

9. Growing the obstacles by the robot's size

The cleanest way to plan is to treat the robot as a single point (its centre) and make every obstacle bigger by the robot's radius. Then the planner only has to keep one point clear of the grown shapes.

Our robot is assumed to be an 18 x 18 inch square. UNVERIFIED (real size not yet measured)

  • Inscribed radius, 9 in. Half of 18. A square that always faces the same way needs 9 in of room from a wall on each side.
  • Circumscribed radius, 12.73 in. The distance from the centre to a corner is 9 x sqrt(2), about 12.73 in.

If the robot turns while it moves, the room it needs from a wall changes between 9 and 12.73 in. A plan that uses 9 in is safe only while the heading is locked. Our assist keeps the heading locked while parking, so the 9 in rule applies. UNVERIFIED (heading lock is a design choice, not built yet)

Hard cells have their centre within 9 in of an obstacle. Soft cells (9 to 14 in) are allowed but cost more (section 8).

Goal cells. Parking needs only that the robot be at least partly in the loading zone (manual rule 10.5.4). So a goal cell is any non-hard cell whose centre lies inside the zone grown by 9 in on every side. The robot body then overlaps the zone.

Zone sizes come from the team's measured field data (about 11 x 22.7 in for red). Some old constants in FieldConstants.java are off by about 1.9 in. Aim for the middle of the zone, not its edge. VERIFIED (research worker, overseer spot-check)

10. The flow field: one Dijkstra, then a lookup

Our robot's goal never moves. So instead of searching for each start, run Dijkstra once from the zone outward. Every cell then stores its distance to the goal. This is the same table as the worked example in section 2.

To drive, the robot looks at its current cell and its neighbours, and steps to the neighbour with the smallest distance. That is the whole rule. For example, from cell (0,0) in the 3 x 3 example, both neighbours have distance 3, so either is a best move. Each step lowers the distance by 1, so the robot always arrives.

  • Fast in the loop. Each control cycle reads about 8 array values. The expensive work is done once, before driving.
  • Forgiving. If the driver pushes the robot somewhere else, the table already knows the best move from there. No new search is needed.
  • Shared. Every starting position uses the same table.
  • Limits. It is static: if a new obstacle appears, the whole table must be rebuilt. Its paths are still grid-shaped, so the robot should follow a smoothed line, not single cells.

Research recommends this as the main planner for the assist. UNVERIFIED for our robot until tested on the real field.

Memory

At 2-inch cells, one distance number (8 bytes) per cell is 5,184 x 8 = 41,472 bytes, about 41 KB. A direction byte per cell adds about 5 KB. At 1-inch cells there are 20,736 cells, about 166 KB for the distances alone. VERIFIED (arithmetic)

Heaps

A binary heap is a tree stored in an array, where each parent is no bigger than its children. Push and pop take O(log n) time. Some heaps are faster in theory, such as Fibonacci heaps, but have bigger constant costs. In one study of Dijkstra on a road map, a 4-ary heap was fastest and a Fibonacci heap about 3 times slower. VERIFIED (that study, on a different computer, not our robot)

Lazy deletion. Instead of changing an entry's priority, push a new copy with the better value and skip the old copy when it comes out. This is simpler and was found to be fast in practice. VERIFIED (research summary)

12. Which planner to use for the auto-park assist

These are the planned settings for the robot code. They are not written yet.

  • OFF: no assist. The driver drives alone.
  • FLOW_FIELD: the main planner. Built once when the program starts.
  • DIJKSTRA: a one-time search, used to check the flow field.
  • ASTAR: the fallback if an opponent blocks the field's route. It searches again from the robot's current cell.
  • WEIGHTED_ASTAR: a faster fallback with a cost promise.
  • THETA_STAR: smoother paths when the robot has time to spare.

13. The time budget: when to start

The robot cannot wait until the last second. It has to accelerate, cruise, and slow down. The lab uses a trapezoid model with a top speed of 60 in/s and an acceleration of 90 in/s^2. UNVERIFIED (limits taken from the team's code; not re-measured on the robot)

if d < 40 in: T = 2 x sqrt(d / 90) else: T = d / 60 + 0.667 s

14. Known simplifications

The lab is a teaching model, not a full simulation of the robot. These are the shortcuts we took:

  • The robot is a point with a locked heading, and its size is assumed (18 in).
  • The hive is treated as solid. The planner never drives under it.
  • Opponents and game pieces are not modelled.
  • Pose error (where the robot thinks it is) is not modelled. The localisation offsets are still placeholders.
  • The time model ignores wheel slip, turning time, and the robot's real acceleration.
  • Zone sizes come from the measured field data, which may differ from the official field by a small amount.
