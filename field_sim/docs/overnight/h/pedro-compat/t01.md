## (3) How demo autos drive the follower
Verified by reading the code. The pattern is the same in each file:
- AutoDrivebase.java:75-89 `followPath(PathChain, holdEnd)` calls `beginMove`, then `SimBridge.publishPath(...)` (:87), then `follower.followPath(chain, holdEnd)` (:88). It is non-blocking: it returns immediately.
- The wait loop is written by hand in the OpMode. ShootWhileDrivingDemoAuto.java:60-67:
  `robot.auto.followPath(path, true, LEG_TIMEOUT_S); while (opModeIsActive() && robot.auto.isBusyOrTimeout()) { robot.update(); ... }`
- `robot.update()` calls `auto.update()` (Robot.java:192-193). That calls `follower.update()` (AutoDrivebase.java:143). This is the only place the follower is ticked, and it happens once per loop.
- Completion check: `isBusyOrTimeout()` (AutoDrivebase.java:178-180) returns `follower.isBusy()` (:152-154) unless the deadline has passed. On timeout, `cancelMove()` (:188-190) calls `holdPoint(getPose())`.
- ProfileDemoAuto.java:82-84 uses the same loop, and :109-115 `sleepWhileUpdating` keeps `robot.update()` running during pauses.
- Chain callbacks: none of the three demo autos use them. I did not grep for callback APIs across the whole tree, so "none used" is only verified for these three files.
- AutoAimDemoAuto.java never touches the follower. It calls `AutoAim.run(robot, this::opModeIsActive, TIMEOUT_S, SHOOT_AFTER, telemetry-callback)` (:38-41). AutoAim.java:73 and :87 define the two `run` overloads. The aiming logic is in AutoAim/AutoAimLogic, which was not read in full.
- Each demo wraps its body in `try { ... } finally { robot.stop(); }` (ShootWhileDrivingDemoAuto.java:49-87; ProfileDemoAuto.java:45-70; AutoAimDemoAuto.java:37-46).

Inferred (not directly read): the Pedro follower does not block, which is consistent with `followPath` returning immediately and with the `isBusy` polling loop above.

## (4) What robot.auto exposes
`public final AutoDrivebase auto;` (Robot.java:112). It is built at Robot.java:136. `Robot.update()` ticks it (:193). `Robot.stop()` releases it (:432).

AutoDrivebase.java public surface:
- `pathBuilder()` returns `follower.pathBuilder()` (:70-72).
- `followPath` overloads (:75, :92, :97, :102, :110). Each takes a PathChain or a Path, plus holdEnd, and optionally a timeout in seconds.
- `holdPoint(Pose)` (:116). `update()` (:124). `isBusy()` (:152) and `isBusy(timeoutS)` (:162). `isBusyOrTimeout()` (:178). `timedOut()` (:183). `cancelMove()` (:188). `moveElapsedS()` (:157).
- `getFollower()` returns the raw Pedro `Follower` (:192-194).
- `getPose()` (:196), `getVelocity()` (:201), `getAngularVelocity()` (:206), `getAcceleration()` (:211), `setPose(Pose)` (:215).
- `getProfile()` (:219) returns the motion profile in use.

Construction: `follower = Constants.createFollower(hardwareMap)` (AutoDrivebase.java:59), then `setStartingPose` (:60). `Constants.createFollower` (pedroPathing/Constants.java:48-54) uses `FollowerBuilder` with mecanum and Pinpoint localizer.

Note: `Constants.java:20-21` says the follower, braking, and PIDF values are still library defaults. The Pedro constants are not measured.

## Compatibility with the requested structure (decision for the lead)
- The current auto structure is plain OpMode plus hand-written polling loops around `robot.auto`. It is already compatible with Pedro: Pedro's `Follower` is used directly through `pathBuilder`/`followPath`/`update`.
- There are no command-group classes to be compatible with. A command-group layer, if wanted, would wrap these calls. It would not replace Pedro. This is an inference from the grep results, not something I verified in a library.
- Pedro 2.1.0 chain callbacks are not relied on (domain facts, OVERNIGHT_RULES.md:25). The current code uses polling and does not depend on them.
