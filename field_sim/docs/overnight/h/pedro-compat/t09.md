## 1. Protocol
- Browser -> run_sim.py: POST /api/pedro/follow (batch), /api/pedro/live/start|step|stop.
- Body (followRequest, pedrofollow.js:25): start {x,y,h deg}; segments from routeToBridgeJson (points, heading mode/start/end in deg, callbacks, waitAfter); optional dt, stride, maxTime, settle, holdEnd, maxPower, robot, constants, pathConstraints.
- pedro_bridge.follow() pipes JSON to `java -cp out:jar PedroFollowSim` and parses one JSON line from stdout. Live mode keeps one Java process per session (JSON lines: init/step/close); max 4 sessions, 300 s idle reap (pedro_bridge.py:210-211).
- Batch response: {ok, source:'pedro-core', finished, endReason, duration, info, events[{t,kind,name,seg}], ticks[{t,x,y,h deg,vx,vy,w deg/s,p[LF,LR,RF,RR],seg,phase}]}.

## 2. How the real Follower is driven (PedroFollowSim.java)
- Real com.pedropathing.follower.Follower, stock FollowerConstants plus overrides from `constants`. PathConstraints(0.99,100,1,1) matches TeamCode Constants.java:46.
- Per group: follower.pathBuilder(pc) -> addPath -> build; follower.followPath(chain, maxPower, holdEnd) (line 272).
- Per tick: physics(dt) -> follower.update() -> getChainIndex() for seg (324) -> monitorCallbacks -> pathEnd when !isBusy() && phaseTicks>2 (326) -> WAIT (waitAfter) -> SETTLE (settle, default 0.3 s) -> DONE; maxTime gives endReason 'timeout'.
- Clock: SimClock advanced by dt. pedro_bridge.py:107-113 string-replaces System.nanoTime/currentTimeMillis in 6 Pedro classes from the sources jar. out/follow/PATCHED exists (glob), so the virtual clock is in use. No sources jar -> -Dpedro.realtime=true (slow).
- Robot model: perfect localizer; wheel math copied from Pedro's Mecanum.calculateDrive; body motion via first-order lags tauX/tauY/tauW with accel clamp. Mecanum defaults xVelocity 81.34056, yVelocity 65.43028 (line 180).

## 3. Units and conversions (checked in code)
- Pedro: inches, radians. Route JSON: radians (pathing.js routeToBridgeJson converts with r*180/PI). Java: degrees in, toRadians on use (lines 191, 217-218).
- followRequest start.h = h*180/PI: correct. responseToTrajectory: h deg -> rad, w deg/s -> rad/s: correct.
- Sampler (PedroSampler) output h in degrees; its `t` is Pedro parametric t, `s` is arc length. Pedro getPathCompletion is an arc-length fraction (tools_java/README.md:12).

## 4. Failure modes
- Jar or JDK missing: follow_available() False -> HTTP 503 {"error"} -> JS `!res.ok` throws -> followRoute returns fallbackTrajectory (source 'js-fallback', approximate:true, error set). Unless opts.fallback===false. Callers must check source/approximate; the fallback is a crude kinematic model, not Pedro.
- javac failure in build_follow -> {"error"} -> same fallback.
- Java timeout: 60 s, or maxTime+30 s in realtime mode -> "PedroFollowSim timed out" -> fallback. The JS fetch has no timeout of its own.
- Not finished within maxTime: ok:true, finished:false, endReason 'timeout'. JS returns it as a normal pedro-core trajectory with no error; caller must check .finished.
- Live: unknown/expired session -> error -> PedroLiveFollower._post throws, no auto re-init. Dead Java process -> "PedroFollowSim live process ended". The 5th session silently evicts the least recently used.
- build_follow rmtree(out/follow) can fail on Windows if a live process still holds the classes (unverified).
- followRequest drops callback `args` that pathing.js:270 keeps (only name/t/ms are forwarded).

## 5. Where the sim can diverge from the robot (highest impact first)
1. Robot installs a custom ProfiledVectorCalculator with SCurveProfile (AutoDrivebase.java:64, follower.vectorCalculator = calculator). The sim uses only the stock vector calculator. Motion-profile behaviour in the sim is NOT the robot's. Largest gap.
2. maxPower: sim always passes maxPower (default 1) to followPath. Robot calls followPath(chain, holdEnd) and never calls setMaxPower. Matches only if the library default is 1 (unverified).
3. Constants: robot Pedro gains are library defaults (Constants.java header says so), and the sim uses the same defaults. Both are unmeasured. TODO: run the Tuning OpMode for velocities and PIDFs. The sim's mecanum velocities are assumed to equal the library defaults (unverified against library source).
4. Motor/body dynamics (tauX 0.18, tauY 0.20, tauW 0.10, maxAccel 220, coastW 8, voltage fixed 12 V) are ASSUMED, not measured. No battery sag, wheel slip, walls/collisions, Pinpoint noise or latency.
5. Callbacks: the sim fires 'callback' events from getPathCompletion monitoring. Per OVERNIGHT_RULES, the robot's chain callbacks never fire, so marker logic keyed on 'callback' works in the sim and would fail on the robot. The sim's 'pedroCallback' mirrors Pedro's chain path, which the README says is also mis-indexed (unverified how it behaves in the sim).
6. Timeouts: robot isBusyOrTimeout uses wall-clock moveElapsedS (System.nanoTime) and cancelMove(). The sim has no per-leg timeout, only maxTime for the whole run. Pedro pathConstraints.timeoutMs is sim-clocked.
7. Marker t: pathing.js:386 places markers at Bezier parameter c.t. The sim compares c.t to getPathCompletion() (arc-length fraction). On curved segments, sim event positions and drawn markers can disagree (magnitude unverified).
8. waitAfter: a sim phase (WAIT). The robot has no equivalent in AutoDrivebase; waiting is OpMode code.
9. Update cadence: sim calls Follower.update every 5 ms; robot calls AutoDrivebase.update once per loop (dt clamped to 0.1 s). PIDF/Kalman behaviour depends on this and is not modelled.

## 6. Chain-index and t polling for markers
- Chain index: SUPPORTED. Each tick has seg = firstSeg + follower.getChainIndex() while following (guarded by getFollowingPathChain()). Live step (n ticks) can be polled.
- Path t / progress: NOT in the tick output (no path-completion or distance field). Only 'callback' events exist, fired when getPathCompletion() >= t or ms elapsed (sim-only). Live mode with n=1 gives per-tick resolution.
- Suggested follow-up (not my file): add pathCompletion (getPathCompletion) and currentPathNumber to each tick in PedroFollowSim.appendTick.
