# t06 Audit of locateMarker / segmentWeights (web/js/autoexport.js)

Scope: read-only. Read docs/OVERNIGHT_RULES.md, web/js/autoexport.js (lines 55-190 and the polling at ~296-307), tests_js/autoexport_marker.test.mjs, docs/overnight/h/pedro-compat/t03.md. Did NOT run node or any test; all numbers below are hand-computed.

## Consumer side (what Pedro-facing code expects)
- Generated poll (autoexport.js:306): fires marker when `chainIdx > seg || (chainIdx == seg && tNow >= t)`. So (seg, t) = (i, 1) and (i+1, 0) both fire at the same physical point; the `>` clause makes boundary ambiguity harmless. Unfired markers are flushed at path end (line 307).
- Pedro semantics per t03 (source read of core-2.1.0-sources.jar, Follower.java): chainIndex starts at 0 in followPath(chain), increments in update() when not busy. Verified in t03 only as read from source.
- UNVERIFIED: what getCurrentTValue() measures (curve parameter vs closest-point projection vs arc fraction). Not covered by t03 or by this audit. Nothing in the repo confirms it.

## Cases (weights = control-polygon or polyline lengths, in inches)
1. weights [10,30,60], T=100, t=0 -> (0, 0). OK.
2. same, t=0.05 -> g=5 -> (0, 0.5). OK.
3. same, t=0.25 -> g=25 -> (1, 0.5). OK.
4. same, t=1 -> g=100 -> (2, 1). OK.
5. same, t=0.10 (boundary seg0/seg1) -> g=10 -> (0, 1), not (1, 0). Convention only; poll's `>` clause makes it safe. Note.
6. same, t=0.40 (boundary seg1/seg2) -> (1, 1). Same convention note.
7. single segment [50], t=0.3 -> n===1 branch -> (0, 0.3). OK (returns raw t, independent of length).
8. single segment, t=1 -> (0, 1). OK.
9. clamps: t=1.5 -> (2, 1); t=-0.2 -> (0, 0); t=NaN -> (0, 0). OK.
10. zero-length first seg, weights [0,40,60], t=0 -> (0, 0) (zero-length seg picked); t=0.4 -> (1, 1). Works, but a zero-length seg 0 would emit BezierLine(p,p) if its two points are identical. Risk, unverified in Pedro.
11. CURVE vs LINE: seg A line (0,0)->(100,0) weight 100; seg B cubic with control points (100,0),(100,60),(160,60),(160,0), control-polygon weight 180. t=0.5 -> g=140 -> (1, 0.222). The polygon length is an upper bound on the true arc length of B, so B is over-weighted. If B's true arc length were A (unknown here; e.g. 120 is an assumption for illustration only), the arc-based answer would be (1, 0.083). MISMATCH if Pedro's completion is arc-based (unverified). Verdict: chord/polygon weighting, not arc length.
12. BENT LINE: seg type 'line' with points (0,0),(30,40),(60,0). segmentWeights counts the polyline (50+50=100), but buildPathCode emits BezierLine((0,0),(60,0)) (length 60) because `s.type === 'line'` uses only first and last points. With weights [100, 50] and t=0.5: code gives (0, 0.75); emitted geometry [60, 50] gives g=55 -> (0, 0.917). BUG: weights and emitted geometry disagree for line segments with interior points.
13. ALL-ZERO weights [0,0,0] (n=3), t=0.5 -> (1, 0.5). Equal-count fallback; OK as a guess.
14. ALL-ZERO weights [0,0,0], t=1 -> seg=min(2, floor(3))=2, t=3%1=0 -> (2, 0). BUG (minor): end-of-path marker maps to start of last segment. Should be (2, 1). Same for [0,0] with t=1 -> (1, 0).
15. Zero segments n=0 -> seg = min(-1, ...) = -1. Marker stored with seg -1: `chainIdx > -1` is always true, so it fires on the first poll. Minor bug, unlikely reachable.
16. Rounding: buildPathCode rounds t to 3 decimals (line 177). t=0.9996 -> 1.000; fires on tNow >= 1.000. Harmless.
17. Floating point: weights [0.1,0.2,0.7], t=0.3 -> g=0.3 vs cum 0.30000000000000004; 1e-9 tolerance absorbs it. OK.

## Verdicts
- Mapping t -> (seg, local t) is consistent with chainIdx ordering (segment index = chain index, same order as emitted addPath calls). OK. Also matches PedroFollowSim.js-style firstSeg + chainIdx usage at tools_java/PedroFollowSim.java:324.
- Boundary convention: OK given the poll's `>` clause (cases 5-6).
- BUG A (case 12): line segments with >2 points: weights vs emitted geometry disagree. Fix in segmentWeights: for type 'line' use endpoints only (or emit a polyline).
- ISSUE B (case 11): control-polygon weighting overestimates curves. Fix would sample each Bezier (e.g. 32-64 points) for arc length, but only if Pedro's getCurrentTValue is arc-based. UNVERIFIED; must check Pedro source (Path / BezierCurve length or closest-point code) before changing.
- BUG C (case 14, minor): zero-total end-of-path maps to (n-1, 0). Fix: if t===1 return {seg:n-1, t:1}.
- Minor (case 15): n=0 should return no marker.
- Test gap: tests_js/autoexport_marker.test.mjs does NOT test the mapping. locateMarker and segmentWeights are not exported, and the tests only assert autoAim strings (startAutoAim, autoAimCmd.update). No assert on marker seg or t. Suggest exporting them and adding cases 1-4, 7, 9, 12, 14.
