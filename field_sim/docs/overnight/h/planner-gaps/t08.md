# t08: autoAim track/timeout audit (planner-gaps, Haiku worker)

Scope: read-only audit. Only this file was written. No code, test or git changes.

## What the code does today (evidence)

- `web/js/autos.js:41` COMMAND_DEFS.autoAim args = `{shootAfter}` only. `autos.js:442` passes the whole `args` object to `adapter.autoAim(args)`, so `track`/`timeout` already reach the runtime IF present in the node. The gap is the schema, not the call site.
- `web/js/autos.js:220-224` validation checks only keys listed in the def. Unknown keys (`track`, `timeout`) are not validated.
- `web/js/autoui.js:227-233` makeNode fills each arg from `spec.default`. A palette-created autoAim node today gets `{shootAfter:false}`. Any new default is written into every new node.
- `web/js/autorunner.js:188-196` runner reads `args.timeout` (seconds) and `args.track`. `_makeAim` (line ~204) passes `timeoutSec: args.timeout` to `makeAutoAim`.
- `web/js/autoaim_cmd.js:28-39,62-70` `makeAutoAim` takes `opts.timeoutSec` and `opts.track`. `Number.isFinite(opts.timeoutSec)` is checked, so `timeoutSec: 0` is accepted literally and times out on the first tick. A default of 0 therefore needs a runner-side mapping (0 means use default). Default sim timeout is `AUTOAIM_DEFAULTS.timeoutSec = 4` (sim-only, `autoaim_cmd.js:31`).
- `web/js/autoexport.js:125-129` `normAutoAim` maps planner node `{shootAfter, seconds}` to command args `{shootAfter, seconds}`. It reads `seconds`, not `timeout`. Mismatch with the runner.
- `web/js/autoexport.js:320-323` timeout comes from `secs(a.seconds)` (<=0 or NaN gives 0), else `AutoAimTunables.TIMEOUT_S`.
- `web/js/autoexport.js:188-194` path-marker stub emits only `startAutoAim(shootAfter)`. Timeout is ignored in marker mode.
- `web/js/ppformat.js:16-19` `sanitizeAutoAimArgs` keeps ONLY `shootAfter`. `track` and `timeout` are dropped on .pp export and import.
- `web/js/scheduler.js:103` `autoAimCmd({seconds, shootAfter, shootSeconds, ready})` is a separate scheduler-style command. It uses `seconds`, not `timeout`. Used by the scheduler tests, not by autos.js.

## Robot side (../TeamCode, verified by reading)

- `TeamCode/src/main/java/commands/autonomous/AutoAim.java`:
  - `run(Robot, BooleanSupplier, boolean shootAfter)` uses `AutoAimTunables.TIMEOUT_S`.
  - `run(Robot, BooleanSupplier, double timeoutS, boolean shootAfter, Runnable perLoop)` treats `timeoutS <= 0` as `TIMEOUT_S`.
- `AutoAimLogic.java:67` constructor `(double timeoutS, boolean shootAfter, boolean transferOnStart)`. No track concept.
- `AutoAimTunables.java:21` `TIMEOUT_S = 3.0` (robot, dashboard-tunable). `:37` `SHOOT_AFTER_MAX_S = 5.0`.
- There is no `AutoAimCommand` class (autoexport.js:~182 TODO says the same). Autoexport uses AutoAimLogic per tick.
- Sim default timeout 4 s vs robot default 3.0 s. Mismatch. Sim value is sim-only. Robot value is a robot tunable, not a measured constant.

## Proposed param schema for `COMMAND_DEFS.autoAim.args` (units: seconds)

| key | type | default | range | meaning |
|---|---|---|---|---|
| shootAfter | boolean | false | - | unchanged |
| timeout | number | 0 | min 0, max 30 | seconds to wait for aim. 0 = use robot default (`AutoAimTunables.TIMEOUT_S`, 3.0) in export and sim default (`AUTOAIM_DEFAULTS.timeoutSec`, 4) in sim. Default 0 is a DECISION (ASSUMED), not a measured value. Max 30 is ASSUMED. |
| track | boolean | false | - | sim-only: keep applying target after ready until next drive ends. No robot equivalent in AutoAimLogic. TODO. |

Runner rule (autorunner.js, not t08 owner): `timeoutSec = args.timeout > 0 ? args.timeout : AUTOAIM_DEFAULTS.timeoutSec`. Do not pass 0 into makeAutoAim.

Export rule (autoexport.js, not t08 owner): `timeout = args.timeout ?? args.seconds` (accept old planner `seconds` for compatibility), `secs()` maps <=0 to default. `track:true` on export: emit a warning comment in the generated Java ("track is sim-only; ignored on robot"). Do not silently drop.

.pp rule (ppformat.js, not t08 owner): `sanitizeAutoAimArgs` keeps `shootAfter` (boolean), `timeout` (finite number >= 0, else dropped), `track` (boolean). Round-trip must be lossless for valid values.
