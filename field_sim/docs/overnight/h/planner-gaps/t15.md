# t15: audit of plannerfield.js and field drawing (read-only)

Scope: web/js/plannerfield.js (107 lines), consumers app.js, pathui.js, pathing.js, tests_js/planner_redesign.test.mjs. Edited nothing else. No git commands run.
Ran: `node --test tests_js/planner_redesign.test.mjs` -> 8 pass, 0 fail. Did NOT run the full suite or a browser screenshot.

## Coordinate transform: correct
- pathing.js:717-719 `toScreen`: `y = oy + (rb.y1 - v) * k`, so y-up Pedro maps to canvas y-down. x and y are separable, so app.js mx/my (820-821) are exact.
- plannerfield.js takes mx/my from the host and never does its own transform, so it inherits the correct mapping. Test at tests_js line 44 uses `20 + (144 - y) * k`, which matches.
- Quarter turn: app.js:818 `fieldToPx` rotates by q*PI/2 about rotCenter (806, 815). Pointer input is un-rotated first (app.js:824). Both are consistent. Test line 113 pins this.
- Alliance: pathing.js:690 gives rotate180 only for blue. app.js:806 `planRot90` gives +1 for blue and -1 for red (red never flips via rotate180). This is intentional but asymmetric, so it should be documented (see Bugs, item 6).

## Bugs (ranked)
1. plannerfield.js:104 overlay halo `strokeStyle = 'rgba(27,27,31,0.95)'` is a translucent colour. It contradicts the header claim at line 2 ("no translucent boxes"). The test (tests_js line 42-51) only checks drawPlannerField, so the overlay is not covered. Fix: use FIELD_COLORS.bg, or add an opaque-colour test for drawFieldOverlay.
2. plannerfield.js:48 and app.js:926 hard-code the hive footprint `72 +/- 24.73, 72 +/- 19.475`, labelled "approximate" at app.js:925. scene.json has `hives.*.pivot` and about 134 `hive_frame` CAD mesh entries, but no 2D footprint. Source: unverified. Mark ASSUMED/TODO, or derive it from scene data.
3. plannerfield.js:66 ball radius fallback `bl.diameter || 2.8`. scene.json ball diameters are 2.774 to 3.599 (counts from grep, not validated against a manual). Balls with missing diameter get a silent constant. Low severity.
4. plannerfield.js:50 `hive[a] || Object.keys(h.states)[0]`: an unknown hive state key silently draws the first state instead of failing. Low.
5. Stale or dead code: app.js:962 (`else if (S.view === 'auto') ... drawPlannerPoses()`) sits in drawMapInner. drawMap returns early for auto (app.js:858), so drawPlannerPoses (887-898) never runs in the planner. The start and end footprints are drawn by pathui.js drawAuto (534, 544) instead. Remove drawPlannerPoses, or call it on purpose.
6. app.js:847 hard-codes `'#1b1b1f'`, which duplicates FIELD_COLORS.bg (plannerfield.js:7). Use the constant so the two cannot drift.
7. app.js:769-779 mapResize: DPR is set from `window.devicePixelRatio` on the `resize` event only (799). Moving the window to a monitor with a different DPR without a resize leaves the backing store stale. Fix: a `matchMedia('(resolution: Xdppx)')` listener. Chrome usually fires resize on zoom, so this is low risk. Not tested.
8. Resize of the planner: app.js:782-788 autoAvail measures the DOM every frame via fitMap (790-798), which is cached by fitKey. Panel-only changes are handled. Verified by reading, not by a browser run.
9. plannerfield.js:79 the dashed cut uses `b.x0 > 0 ? b.x0 : b.x1`. This is correct for both halves (blue cut at 72, red cut at 72). Not a bug.
10. plannerfield.js:92-93 the gizmo offset does not clamp when the free area is smaller than about 60 px. Low.

## Alliance mirroring and DPR: summary
- DPR: app.js:770-772 sets backing store = innerWidth*dpr and setTransform(dpr). ui.css:35 sets the canvas to 100vw/100vh, so CSS size is correct. drawPlannerView uses CSS-pixel W/H (app.js:843), which is correct under that transform.
- Resize: mapResize (769-779) runs on window resize. Auto mode also re-measures each frame. OK.

## Duplicated drawing code (file:line)
- hull(): plannerfield.js:14-19 and app.js:830-835. Identical.
- poly(): plannerfield.js:33-37 and app.js:836-840. Near-identical; app's version also sets dash.
- Hive footprint and cell loop: plannerfield.js:46-56 and app.js:925-933. Same logic; different colours and line widths.
- Flower ring: plannerfield.js:57-61 (orange ring, radius max(4, 3.2k)) and app.js:935 (filled amber dot, radius max(3, 2.2k)). Same flower drawn two different ways.
- Field floor and border: plannerfield.js:30-32 and 71-81 versus app.js:904-906 and 911 (`#0d1220` background, `#262d40` floor). Two palettes for the same field.
- Ticks and grid: app.js:870 `ticksIn` versus pathui.js:550-557 `drawGrid`/gridLines.
- Robot footprint: pathui.js:512-523 `robotOutline` and app.js:872-879 `drawFootprint`. Both draw an 18 in footprint with a front bar, using different styles. The angle conventions differ (app.js:873 `planFlip() ? PI-h : -h` versus pathui `screenAng`, not checked in full).
- Trajectory and poses: pathui.js:526-548 `drawAuto` covers trajectory, anchors, markers and start/end (the live version). app.js:887-898 is the dead copy (item 5).
- Colours repeated as literals: `#ff9800` (plannerfield.js:10 `element`, pathui T.warn, app.js:896), and ball colours `#ff9a3d`/`#d9b92e` (plannerfield.js:67) with no FIELD_COLORS entry.
- autoui.js: no canvas, `getContext`, or field drawing. The brief's "autoui re-implements field drawing" is NOT true. It only builds the panel DOM. Verified with grep for getContext across web/js.

## Refactor proposal
Create `web/js/fieldpaint.js` (pure canvas, no DOM) with:
- `hull`, `polyPath(ctx, pts, mx, my, fill, stroke, lw)`, `ticksIn`, `hiveFootprint(hiveSpec)`, `hiveCells(ctx, scene, stateKey, env, colours)`, `flowerRing(ctx, c, r, colour)`, `ballDot(ctx, pos, r, colour)`, `robotFootprint(ctx, x, y, h, env, fill)`.
- plannerfield.js keeps only `drawPlannerField` (the flat style) and `drawFieldOverlay`. It calls fieldpaint helpers with FIELD_COLORS.
- app.js drawMapInner (the non-auto view) uses the same helpers with its own palette passed in as an argument, so the palette is the only difference.
- pathui.js keeps the editor-specific trajectory drawing (drawAuto, dotted, tags) and imports `robotFootprint` and `hiveCells`.
- Delete app.js 830-835 (hull), 872-898 (drawFootprint, drawPoseMarker, drawPlannerPoses) once the helpers exist.
- Tests: add an opaque-colour check for drawFieldOverlay (item 1), and a parity test that hiveCells output is identical for the planner and the 2D map (same polygons, different colours).
