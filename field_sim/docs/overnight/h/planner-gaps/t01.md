Scope: read web/js/pathing.js, web/js/pathui.js, web/js/app.js, web/js/collision.js, web/data/colliders.json. Edited nothing else. Ran: read/grep, and one node read of colliders.json (no tests run, no git).

## How the check works (pathing.js:295-302)
- Runs only when obstacles.length > 0. For each sample from `sampleRoute(route, 1)` (1 in steps, pathing.js:147), and each obstacle `o`, it tests the CENTRE point `p.x, p.y` against `o.minX..o.maxX`, `o.minY..o.maxY` (line 298).
- Shape: axis-aligned box only (AABB). No circles, no polygons. `o.name` is never set for collider boxes, so the message falls back to `obstacle ${oi + 1}` (line 299). That number is an index into the filtered list, not a hive name.
- Dedupe key is `seg:oi`, so at most one warning per segment per obstacle (line 297-298).
- Robot footprint is NOT used. The check ignores `ROBOT.halfX/halfY = 9` (collision.js:3) and the heading `p.h` that sampleRoute already returns (pathing.js:151).

## Where obstacles come from
- web/js/app.js:111 `fieldData.boxes = colliders.boxes.filter(zMax > 3)`, with flower boxes trimmed to a 1 in plate (trimFlower, app.js:103-110).
- app.js:651 `createPathEditor({..., getObstacles: () => fieldData.boxes.filter(b => b.zMax > 3)})`.
- web/js/pathui.js:184 `obstacles()` returns the host array (falls back to ed.obstacles).
- pathui.js:606-607 (draw) and :785-786 (panelHtml) both call `P.validateRoute(route, ed.obstacles)`.
- Data (web/data/colliders.json, node read): bounds 1.326..142.674; 4 `hive_frame` boxes with zMax 18 (e.g. x 47.36..53.54, y 52.52..61.76; x 47.36..53.54, y 82.24..91.48; x 90.47..96.65, y 82.24..91.48; x 90.47..96.3, y 52.93..61.76), 2 low `hive_frame` rails (zMax 2.15, excluded by the filter), 4 `flower` boxes (zMax > 3). 0 circles.
- So the hive is NOT one big rectangle. It is 4 tall corner posts (about 6.2 x 9.2 in each), plus the flower plates. The "hive" obstacle the planner sees is those posts only.

## Answers to the question
1. Shape: AABB boxes from colliders.json. No padding or bounding-box inflation is applied in validateRoute. The boxes are the real collider extents, so "too large bounding box" is not the cause.
2. Robot footprint: not used at all. The test is centre-in-box, so it UNDER-reports. A path whose centre stays 9 in from a post but whose 18 in body clips it gives no warning. A path whose centre enters a post box does warn, and that is a true collision.
3. Frame: pathing.js and collider data are both in the Pedro frame (inches, origin audience-left). No mismatch found, so the warning location is geometrically consistent with the sim's collider.
4. Why the user sees a warning near the hive: most likely the centreline is genuinely inside one of the 4 tall post boxes, or inside a flower plate (1 in deep, at the wall). Unverified: I did not render the specific route, so I cannot confirm which box fired. The label "obstacle N" gives no clue which one.
