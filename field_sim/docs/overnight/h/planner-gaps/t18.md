# t18: autoui.js vs pathui.js delete/collapse/selection audit

Scope: read-only audit. Edited nothing else. Method: read autoui.js (state, commit/record/restore, deleteAuto/deletePath, nodeRow, handleKey, destroy) and pathui.js (handleKey, deleteSelection, act(), panel click handlers), plus app.js:588-592 (window keydown). Also grepped addEventListener and removeEventListener in both files. NOT run: no node tests, no browser. Everything below is from reading the code, so each claim is "code reading, unverified at runtime".

## Concrete bugs (ranked)

1. Delete and Ctrl+Z fire in BOTH the auto planner and the path editor (autoui.js:913-918, app.js:590).
   - autoui handleKey checks only `active && !editable(target)`. It never checks `editing`, so it runs while a path is open in the right pane.
   - Event order: autoui registers on `document` (autoui.js:922), app.js on `window` (bubbles after document). The autoui handler runs first, then pathEditor.key runs.
   - `openPath()` (autoui.js ~470) does not clear `selected`, so a command node selected before opening a path stays selected.
   - Failing scenario: select a command node in the auto tree, click a path row in the left list (sets active=true via mousedown), press Delete with focus on body. autoui deletes the selected command node (deleteNode, line 916), and pathEditor deletes the selected waypoint. Two different documents change from one keypress.
   - Ctrl+Z in path mode: autoui `undo()` (line 917) and pathEditor `ed.undo()` (pathui.js:146) both run, so one press undoes two histories.
   - Fix idea (not applied): in handleKey, `if (editing) return;` at the top, and clear `selected` in openPath.

2. Deleting the auto that is open re-saves it on the next edit (autoui.js:384-395 deleteAuto, line 200-206 autosave).
   - deleteAuto sets `libName = null` but leaves the open `auto` in the editor.
   - Next commit() calls autosave() (lines 202-209). Since `libName` is null and the name is no longer in the list, autosave runs `librarySave(st, auto)` (line 207) and the auto reappears.
   - Failing scenario: open "A", press trash on "A" in the Autos list, then drag any command in. "A" is back in the library. Pressing Undo on the delete bar then saves a copy as "A (2)" (uniqueName at line 388), so the user gets two autos.
   - Fix idea (not applied): on deleteAuto of the open auto, either clear the editor (newAuto) or mark it as unsaved so autosave does not resurrect it.

3. Undo of a path delete loses the path's markers (autoui.js:419-430 deletePath, line 424 and 177).
   - Line 424 deletes `auto.paths[id]`, which holds the event markers, via commit. Undo (line 425) restores only the library route. It does not restore the auto copy.
   - syncPaths (line 177) recreates the copy as `{ segments, markers: [] }`.
   - Failing scenario: a followed path with a custom event marker is deleted from the library and Undo is pressed. The path comes back, but its markers are gone and the follow node still points at it.
   - Fix idea: capture `auto.paths[id]` before the commit and restore it inside the undo closure.

4. Only one undo slot (autoui.js:351-354 showUndo). `undoBar` is overwritten by each delete.
   - Failing scenario: delete auto "B", then within 8 s delete path "P". The Undo bar now offers only the path. "B" cannot be undone, and the earlier undo is silently dropped.
   - Severity low, may be intended. Flagged for the owner to decide.

5. Path editor event delete skips the lock check (pathui.js:960 and pathui.js:372).
   - Lines 961 and 962 both check `isLocked(sg)`. Line 960 (`data-cbdel` panel button) does `route.segments[ed.sel].callbacks.splice(...)` with no lock check. Line 372 (right-click or Delete-tool removal of an event) calls `P.removeEvent` with no lock check.
   - deleteSelection (pathui.js:436-446) does check the lock for events, so the bypass is inconsistent.
   - Failing scenario: a locked path has an event marker. Clicking its x in the events panel removes it, which the lock is supposed to prevent.
   - Also line 960 uses `ed.sel` at click time, not the segment it was rendered from. It is only wrong if `ed.sel` changed without a re-render (low).

6. Path editor delete has no undo, unlike the planner (pathui.js:895-898 `pdel` vs autoui.js:430-433 `deletePath`).
   - `pdel` calls `lib.remove(n)` and shows only a toast. The planner's path delete uses showUndo.
   - Low, but it is the same concept handled two different ways.

## Checked and OK

- Typing: rename input (autoui.js:335) and both handleKey functions skip INPUT/SELECT/TEXTAREA. Row Delete (autoui.js:342) stops propagation, so no double fire.
- Row buttons: btn() stops propagation (autoui.js:289), so trash/up/down/toggle do not also select the row.
- Selection after delete: commit() (line 216) and restore() (line 222) clear `selected` if the node is gone; select() (line 609) and deleteNode (line 608) guard. No out-of-range index found.
- Undo/redo: record() dedupes and caps at 200 (line 199-203). restore() does not push history. No issue found.
- Listener leaks in autoui: rows are rebuilt each render with their listeners. Doc keydown/mousedown are removed in destroy() (line 945), and the ResizeObserver and pathLib subscription are released too.
- pathui.js has no addEventListener/removeEventListener calls; panel handlers are reassigned with `onclick` on each render, so nothing accumulates.

## Minor / low

- autoui.js:790-794 timeline drag removes its doc listeners only on mouseup. A missed mouseup keeps seeking on every mouse move.
- autoui.js:923 mousedown listeners on the three panes are not removed in destroy(). Only matters if the planner is created twice (app.js:690 creates it once).
- autoui.js:116 `collapsed` is never pruned on delete or undo. Stale ids are harmless.
- pathui.js:445-449 Delete with one segment left empties the route. The pdel path (line 896) keeps at least one path; deleteSelection does not. Downstream handling unverified.
