# t02: Where planner obstacle shapes come from

Scope: read-only. Ran: Grep over web/js, node read of web/data/colliders.json and web/data/scene.json, read of tools_js/extract_colliders.mjs. No tests run, no edits outside this file, no git mutations.

## Obstacle builders (every site)
1. web/js/app.js:111 `fieldData` = colliders.json boxes with zMax > 3 (RAIL_MAX_Z), flower boxes passed through `trimFlower` (1 in thick back plate).
2. web/js/app.js:112 `obstacles = buildObstacles(fieldData)` (collision.js:7). Drops boxes with zMin >= 18 or zMax <= 0. Output: AABB boxes (+cx,cy,hx,hy), circles, bounds. Used by physics `resolveRobot` (app.js:400, 413). Not used by the planner.
3. web/js/app.js:651 `createPathEditor({ getObstacles: () => fieldData.boxes.filter(b => b.zMax > 3) })`. This is the planner obstacle list. Raw AABB objects `{minX,minY,maxX,maxY,kind}` in Pedro inches.
4. web/js/pathui.js:184 `obstacles()` wraps getObstacles; falls back to `ed.obstacles` on error. Consumed at pathui.js:568, 606 (red dots on route points inside boxes) and 785-786 (`P.validateRoute(route, ed.obstacles)`).
5. web/js/pathing.js:278 `validateRoute` (tests route centreline samples, `sampleRoute(route,1)`, against each box; warns "passes through obstacle").
6. Shot-side (not planner): app.js:347 `hiveTall` (hive_frame boxes, zMax 80), app.js:376 and 751 use raw `fieldData` as ballistic obstacles. Not in scope for the planner.
7. tests_js/*.test.mjs read colliders.json directly (collision, shotrules, etc.). Not production.

## Mismatches and risks (ranked)
1. **No robot footprint in the planner (high).** validateRoute tests a point (route centreline) against each AABB with no inflation by the 9 in half-extent (collision.js ROBOT halfX=halfY=9). Physics (`isFree`, `resolveRobot`) uses the full 18x18 rotated box. A planned path can clip a leg or flower by up to 9 in and show no warning. Also checks no heading.
2. **Planner bounds 0..144 vs sim walls 1.326..142.674 (medium).** `inb()` allows waypoints 1.3 in closer to the glass than physics; the robot centre cannot reach them (physics pushes it out).
3. **Floor rails excluded (medium, policy conflict).** Planner and physics both drop the 2.15 in rails (app.js:111, RAIL_MAX_Z=3). README.md:48 says the robot "cannot drive through ... hive rails", and also says "team decision pending" for the rails. Code and README disagree. Planner treats the rails as drivable, same as physics.
4. **Flower trimmed to 1 in plate (medium).** trimFlower (app.js:~103) is for ball stacking, but it applies to the planner too (app.js:111 feeds getObstacles). The planner therefore sees flower bases as ~1 in thick, while raw extraction says ~5 in deep (e.g. left flower raw x 1.33..6.37). A route can cross the flower base area 2.3..6.4 in. Planner and physics agree, both are wrong if the flower base is solid to the robot.
5. **Two obstacle paths (low, risk of drift).** Physics uses buildObstacles (z_cap filter, app.js:112). Planner uses raw filter(zMax>3) (app.js:651). Same set today (no box has zMin >= 18). A future box with zMin >= 18 would reach the planner but not physics.
6. **Leg footprints are merged AABBs (unverified magnitude).** extract_colliders.mjs merges CAD slices with slack 1.3 (mergeBoxes, line ~104). The bbox can be larger than the true leg outline. Not measured against the CAD here. Label unverified.
7. **Hive body not in the planner.** Acceptable (z 30.65 > robot height 18, comment-sourced). Not verified by a test.
8. Circles: buildObstacles and pathing support circles only in buildObstacles. Planner ignores circles. colliders.json has 0 circles, so no current effect.
