# t10 Pedro compatibility audit of autos output (read-only; nothing else edited)

## Answer
Exported Java does NOT use chain callbacks or a command library; it emits a tick-driven state machine with done-flags. That is compatible with Pedro 2.1.0 in principle, but there are concrete gaps below (two HIGH).

## What the repo uses
- Command library: none on the robot. grep of ../TeamCode (.java, gradle) finds no SequentialCommandGroup, ParallelCommandGroup, ParallelRaceGroup, ParallelDeadlineGroup, FTCLib (com.arcrobotics) or NextFTC. Deps: ../build.dependencies.gradle has `com.pedropathing:ftc:2.1.0`, telemetry 1.0.0, fullpanels 1.0.6 only.
- Planner groups: web/js/autos.js:24 imports `./scheduler.js` (FTCLib-shaped sim scheduler: sequential/parallel/race/deadline, autos.js:478-482). This is sim-only; it is not emitted to Java.
- Exporter default: web/js/autoexport.js:431 `style = 'statemachine'`. Ivy style (autoexport.js:386-453) is optional, not in the gradle deps, and its names are self-marked UNVERIFIED (autoexport.js:448-452).
- Robot follow API: TeamCode/src/main/java/commands/autonomous/AutoDrivebase.java:75-88 (`followPath` wraps one `follower`), :178 `isBusyOrTimeout`.
- No callbacks in TeamCode Java (grep for addParametricCallback / addCallback / callback: no hits in robot code). pathing.js:527-548 and autoexport.js:171 both state polling, not callbacks. Good.

## Concrete incompatibilities (ordered by severity)
1. HIGH, condition names accepted by the sim but not mapped to Java. autos.js:61-69 `parseCondition` accepts `timeElapsed:S`, `hopperFull`, `hopperEmpty`. autoexport.js:266-286 `conditionExpr` maps only ballCount, flywheelReady/shooterReady/aimed, readyToFire, ballsFull/full/isFull, gateOpen/gateAtTarget, flowerDeployed/flowerIdle. Anything else hits the default at :280-284 and emits a stub that returns false. With timeout 0, the waitUntil branch returns false forever (autoexport.js:315 "no timeout set"), so the robot hangs in that state. Fix: map the three names (or reject them at validation) and make timeout 0 on waitUntil a validation error.
2. HIGH, two follow nodes running in parallel/race/deadline share one follower. autoexport.js:349-373 runs each child independently. Each `follow` state (autoexport.js:308) calls `robot.auto.followPath`, which resets the single Pedro follower and the shared `moveTimeoutS`/`timedOut` in AutoDrivebase.java:75-88, :178-184. Sim accepts it (scheduler `parallel`, scheduler.js:165-166; autos.js:470 builds parallel(follow, markers)). No validation rule in autos.js rejects it (grep for "parallel"/"overlap"/"concurrent" finds no check). Fix: add a validation error for overlapping follow nodes.
3. MEDIUM, timed path markers silently dropped on the robot. autoexport.js:254-257 turns `shoot`/`shootAll` markers into a TODO comment. Sim runs them as parallel branches (autos.js:465-470). Divergence between sim and robot.
4. MEDIUM, group markers are flattened. autoexport.js:260 flattens sequential and parallel marker children into one list of instant statements, so ordering and waits are lost. Any wait, waitUntil, follow, or race/deadline inside a marker becomes a TODO (autoexport.js:262).
5. MEDIUM, .pp export drops the command tree. ppformat.js:51 emits `sequence` with path items only. ppToRoute drops `wait` items (ppformat.js:96). Commands, groups and waitUntil are not representable in the .pp file. Callbacks ride along in per-line `biobuzz` extras (ppformat.js:37, :118); the Visualizer may ignore them. Key names are self-described as NOT verified (ppformat.js:5-7).
6. MEDIUM, marker timing semantics unverified. Markers are polled via `getChainIndex()` and `getCurrentTValue()` (autoexport.js:305-306). The t of a path marker is mapped by arc length (`locateMarker`, autoexport.js:75-86), but Pedro's t is per-curve parametric. Callback markers round-trip consistently (autos.js:405-406 builds frac from parametric t), but free-standing `path.markers` on curved segments can fire at the wrong spot. Pedro 2.1.0 getChainIndex and getCurrentTValue semantics: UNVERIFIED in this audit.
7. LOW-MEDIUM, single-point segments become zero-length paths. autoexport.js:161 emits `new BezierLine(START_POSE, START_POSE)` for a segment with fewer than 2 points. That is a silent wrong path. Should be a validation error.
8. LOW, cancel of a follow does not flush pending markers (autoexport.js:308 cancel method). Race/deadline cancellation can drop a marker that was not yet polled. Probably minor, since poll runs before the busy check.
9. LOW, Ivy style cannot run as generated. Dep line autoexport.js:28 is not in build.dependencies.gradle. Ivy API names are UNVERIFIED (autoexport.js:448-452, :466, :483).

## What is correct
- Path markers are never added to the PathBuilder (autoexport.js:171), so no dead chain callbacks.
- waitUntil timeout path (autoexport.js:315) and FOLLOW_TIMEOUT_S safety (autoexport.js:458) bound most hangs, except item 1.
- Group semantics match the sim: parallel ends when all end (autoexport.js:349-353; scheduler.js:165-166), race ends on first, deadline ends on the chosen branch and cancels the rest (autoexport.js:360-373).
- autoAim is non-blocking and stepped per tick (autoexport.js:186-195), so it works in parallel.

## Could not verify
- Pedro 2.1.0 API names used by the exporter (BezierLine, setLinearHeadingInterpolation, getChainIndex, getCurrentTValue). The header claims they were checked against core-2.1.0-sources.jar (autoexport.js:9-10); I did not re-check the jar.
- Whether Pedro's chain index is 0-based and whether it resets after a chain completes.
- No Java compile and no robot run were done. I only read files and grepped.
