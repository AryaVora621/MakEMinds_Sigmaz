# t04: Point Towards Zones and Path Optimizer placeholders

Scope: read-only audit. Nothing edited. Only grep/read run (no tests run, no screenshots).

## Verdict
- **Point Towards Zones: REMOVE (or keep as disabled note).** Implementing it is possible in the sim model but not in the Pedro export without a segment-splitting exporter change, and no real use case is in the repo.
- **Path Optimizer: REMOVE.** No optimizer exists in the sim. The genetic optimizer lives only in `third_party/visualizer-src/src/lib/optimizer/optimizer.ts` (vendored, not wired into `web/`).

## Can point-towards use existing heading code?
- `web/js/pathing.js` `resolveHeadings` (l.109) and `headingAt` (l.123) only support modes `tangent | constant | linear`. Start/end anchors come from `seg.heading.start/end`.
- `rotationAt` (l.450) interpolates between rotation targets (`seg.rotations`, l.432-461). It accepts an explicit heading per target only, not a point. A point-towards mode would need a new heading mode or a computed `h = atan2(P.y - y, P.x - x)` per sample. That computation is ~5 lines inside `headingAt` (l.123) or `sampleRoute` (l.147).
- Sim-side: feasible. `sampleRoute` would need a `towards` field on the segment and a per-sample branch. `pathui.js` panel card at l.793 and the `addTip` / `noop` action would also change.
- Export: `web/js/ppformat.js` l.32-35 writes only `tangential | constant | linear` headings from `resolveHeadings`. A point-towards heading has no `.pp` type and would be a `biobuzz` extra that the Visualizer ignores.
- `web/js/autoexport.js` l.165-168 writes `setTangentHeadingInterpolation`, `setConstantHeadingInterpolation(start)` or `setLinearHeadingInterpolation(start, end)` from the raw `s.heading` object, not from resolved headings. Pedro 2.1.0 (per repo comments) has no point-towards setter. Exporting a per-sample heading would mean splitting each segment into many short Bezier segments (one per heading sample) and emitting a `setLinearHeadingInterpolation` per piece. That is a real change to the Java generator, untested against a robot.
- Pre-existing gap (unverified impact): rotation targets (`seg.rotations`) are simulated but **not exported** to Java. `ppformat.js` never reads `s.rotations`, and `autoexport.js` never reads them either (grep l.1-170). Point-towards would share that gap unless the exporter is fixed.
- Pedro 2.1.0 API details were not checked: no vendored Pedro source found in this audit, so "no point-towards setter" comes from the repo's own comments (`autoexport.js` l.165-171, `ppformat.js` header l.10), not from Pedro docs. Unverified against the Pedro source.

## Risk
- Implement point-towards: medium-high. Touches `pathing.js` (sample/heading), `ppformat.js` (export), `autoexport.js` (Java generator), `pathui.js` (panel), and needs robot-side testing. Java side needs a lead decision.
- Remove placeholder cards: low. Affects only UI text.
- Possible bug to flag (unverified): `autoexport.js` l.168 uses `h.start || 0` and `h.end`, not resolved headings. A linear segment whose `heading.start` is undefined (inherits previous end) would export heading 0 instead of the resolved value. Needs a test.
