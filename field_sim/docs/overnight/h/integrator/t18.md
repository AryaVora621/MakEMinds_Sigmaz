Scope: read docs/overnight/flower-mech.md, docs/overnight/flower.md, web/js/flowerarm.js, web/js/flowerarm3d.js, web/js/app.js, web/js/autos.js, web/js/autorunner.js, web/js/robotmodel.js. No files edited. No browser render run.

## 1. States and G toggle
- Logic states (flowerarm.js): `stowed`, `deploying`, `deployed`, `stowing`. Progress 0..1, eased. Timing deployS 0.45, stowS 0.45 (data/flower_arm.json, ASSUMED per docs).
- `toggle()`: from `stowed` or `stowing` it calls `deploy()`; otherwise `stow()`. Deploy and stow are ignored while already in the target direction.
- app.js:595 binds `k === 'g'` to `flowerArm.toggle()`. Only active when `S.view === '3d'` and no Ctrl/Meta/Alt. Typing in inputs is excluded. index.html:213 documents G.
- `deploy()` resets `fedCount` and `feedT`. It does not reset while already deployed.

## 2. Auto commands and snapshot/restore
- Autos can deploy/stow: autos.js:43-44 (`flowerDeploy`, `flowerStow`, duration 0.5 s) -> autos.js:444-445 -> host `flower(deploy)` at app.js:674 -> `flowerArm.deploy()/stow()`. Returns true immediately; the auto does not wait for `deployed`. The 0.5 s duration is a guess that roughly matches deployS 0.45.
- autorunner.js:186 forwards `flower(d)` to the host. The autorunner itself has no flower logic.
- Snapshot/restore: app.js:657-659 `snapshot()` returns `{auto:true}`; `restore()` only calls `prepareAutoRun()` and resets the robot pose. It does NOT read or reset `flowerArm`.
  - Stop/Restart: autorunner.reset() -> host.restore -> then `resetAllState()` -> `resetField()` (app.js:550) calls `flowerArm.reset()`. So Stop does stow the arm, but only through the shared reset path, not through restore.
  - seek(t) (autorunner.js:289): calls host.restore(snapshot) and re-simulates. The flower state is NOT rewound. An arm deployed in the original run stays deployed (fedCount and pending balls too) after seek. This is a real gap for seek exactness.
- Autos therefore cannot leave the flower in an incorrect state on Stop, but seek can.

## 3. Wiring gaps in app.js
1. (seek) Flower state is outside snapshot/restore: see section 2. Fix suggestion: include `{ state, progress, fedCount, feedT, _pending }` in the snapshot and restore it in `restore()`. Owner: app.js / autorunner owner (not edited).
2. No on-screen flower button. The only controls are the G key and the auto/planner Mechanisms list (autoui.js:36). Grep found no toolbar or `btn-flower` in web/index.html.
3. Auto `flowerDeploy` does not wait for `deployed`. A planner step after it can feed before the arm is down (feed requires progress >= 0.9, so feeding simply waits). Behaviour is safe; timing is not checked.
4. `flowerArm.update(dt)` runs every frame (app.js:1069) but `feedFromFlower` only feeds while `deployed` or `deploying`, so this is fine.
5. Balls are fed only when `inVolume` of the flower scoring box and `findFlowerContact` hit (app.js:1070). The autos never call feed directly, so auto flower behaviour depends on the robot pose reaching the flower opening.
6. Java side: autoexport.js:102-103 and 285-286 emit `robot.flower.deploy()/stow()`, `isDeployed()`, `isBusy()`. TeamCode FlowerMech was not read here (out of scope). Unverified that these names exist in TeamCode.
