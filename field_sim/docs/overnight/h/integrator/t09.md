# t09: Pedro compatibility of AutoRunner trajectory replay (read-only review)

Scope: read web/js/autorunner.js, pedrofollow.js, pedrosample.js, docs/overnight/pedro-compat.md, plus the call chain
(autoui.js:153-155, pathing.js:477-495). I ran nothing (no tests, no sim). All findings are from reading the code.

## Answer
Partly. Frame, units and heading interpolation are right, but the bridge-down path does NOT fall back to the trapezoid
model; it replays a crude kinematic approximation as if it were real Pedro motion (B1). Several input-validation gaps
exist (B3-B5).

## Checked and OK
- Units: Pedro inches / radians throughout. pedrofollow.js:42 converts bridge degrees to rad; pedrosample.js:16 converts h.
- Heading wrap in poseAt: autorunner.js:53 interpolates the shortest arc. Hand-check a.h=3.1, b.h=-3.1, f=0.5 gives ~pi. Correct.
- Replay velocity heading: autorunner.js:148,162 wrapAngle(p.h-last.h)/dt. Correct.
- Duplicate times: pathing.js:493 guards b.t>a.t; pedrofollow.js:90 uses `|| 1`. No division-by-zero found.
- Time scaling: replay advances by the same dt that step() scales by runner.speed (autorunner.js:154, :279), so replay and
  trapezoid both scale with speed. No mismatch inside the runner.
- Trapezoid profile (autorunner.js:170-171): braking sqrt(2*a*remaining) plus 2 in/s floor. No overshoot found.

## Bugs (ranked)
B1 HIGH. Bridge down: js-fallback trajectory is replayed as Pedro motion; trapezoid never used.
  Chain: pedrofollow.js:76-78 catches any error and returns fallbackTrajectory (source 'js-fallback', length > 1).
  pathing.js:482 accepts any array with length > 1 and labels it source 'pedro-follower'. autoui.js:155 passes it on.
  autorunner.js:118-122 (_setTraj) never checks .source or .approximate, so followRaw (:144-148) replays it.
  Only a failed import (pathing.js:484) reaches localTrajectory; a down bridge never does.
  Minimal failing input: fetch rejects (or returns 500) -> followRoute returns the js-fallback traj -> AutoRunner.trajs[id] set
  -> robot follows followSim's crude path. Matches the warning in pedro-compat.md ("should be flagged in the Pedro tab"), which is not done.
  Fix (not applied, not my file): planTrajectory should call followRoute with fallback:false, or check traj.source === 'pedro-core'.

B2 HIGH (probable). Start heading of every path is the auto start heading, not the previous path's end heading.
  autorunner.js:90 builds route.start.h = this.auto.start?.h for every path id. That route goes to the trajectory sampler
  (autorunner.js:112), then planTrajectory uses route.start as startPose (pathing.js:481), then followRequest sends body.start.h
  (pedrofollow.js:28).
  Minimal input: auto.start.h = 0; path A ends at heading pi/2; path B starts at the same point with heading pi/2.
  The sim starts B at h=0, and replay setPose (autorunner.js:147) snaps the robot 90 degrees at t=0.
  Unverified: whether the bridge uses start.h for the first segment's heading (routeToBridgeJson in pathing.js:211 not read).

B3 MEDIUM (latent). Trajectory-only replay throws.
  autorunner.js:142-143 checks `pts` (samples) before the trajectory branch at :144. With no pathSampler, _samplePath never
  stores samples (autorunner.js:95-97), so followRaw throws "No samples for path" even when a trajectory exists.
  Minimal input: new AutoRunner({host, trajectorySampler: r => [{t:0,x:0,y:0,h:0},{t:1,x:10,y:0,h:0}]}).load(auto).prepare().start() -> error.
  Production always passes pathSampler (autoui.js:830), so this is latent. Fix: move the `if (!pts)` check into the trapezoid branch.

B4 MEDIUM. Unsorted trajectory times: total duration taken from the last array element.
  autorunner.js:122 sets T = tr.at(-1).t. autoui.js:165 does the same for the timeline.
  Minimal input: t=[0,1,0.5], x=[0,5,3]. T=0.5, so replay ends at x=3 and never reaches x=5.
  _setTraj validates finiteness only (:120). Fix: sort by t or use Math.max over t.

B5 MEDIUM. Non-monotone sample s: path length from last element, not max.
  normalizeSamples keeps caller-given s (autorunner.js:42-43). followRaw uses L = pts.at(-1).s (:158), and poseAt binary-searches (:51).
  Minimal input: samples x=[0,10,20], s=[0,10,5]. L=5, so the robot stops at x=5, not x=20.
  Possible source: pedrosample.js:16 uses s = off + q.s, and pedrosample.js:12 sets off=0 when sg.offset is missing, so
  segment 2 restarts at s=0. Unverified whether the bridge always sends offset (I did not find the bridge's Python source with
  a grep for "offset" under field_sim; the Java/tools side is not in scope).
  Fix: use Math.max over s for L, and/or reject non-monotone s in normalizeSamples.

B6 LOW. Zero-length / empty path.
  - Single-point or zero-length path: L=0 -> fin at start (autorunner.js:166). OK.
  - Zero segments: followRoute throws at pedrofollow.js:67, outside its try, so planTrajectory's catch (pathing.js:484) returns
    localTrajectory and the runner falls back. OK.
  - Zero segments on the sampler side: pedrosample.js:58-60 returns sampleRoute(route, step) samples. If that is an empty array,
    normalizeSamples throws (autorunner.js:38), samples[id] is never set, and followRaw throws (:143). The auto then errors
    instead of skipping the path. Unverified: pathing.js sampleRoute was not read.

B7 LOW. poseAt single-point case returns raw h (autorunner.js:50) with no wrapAngle, unlike the 2+ point case (:53). Cosmetic.

Timing note (not a runner bug): autoui.js:163-165 refines the Gantt duration from the Pedro trajectory only after the async
call returns. Before that, pathTime (autoui.js:169) may show a different duration than the replay. I did not confirm where
pathInfo(id).time comes from, so this is unverified.
