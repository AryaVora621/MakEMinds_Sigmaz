# t04: Transfer-off command feasibility

Scope: read-only audit (Grep/Read). Nothing edited, no git, no tests run.

## Answers

1. **Is there a transfer on/off state already?**
   - **Sim host (partial):** `web/js/app.js:654-675` has `S_AUTO.transfer` and `autoHost.transfer(on)`. The comment at :669 says "the sim has no transfer gate yet, so the state is recorded and logged only". Nothing moves balls. `:705` resets it to false per run, and `:735` makes Stop turn it off.
   - **Runner (partial):** `web/js/autorunner.js:7` documents `transfer(on)` as a host method. `:210` maps it, inside the autoAim adapter only (`:187` autoAim doc). No command in `autos.js` calls it directly.
   - **autoAim path:** `autos.js:41` says autoAim "turn[s] on the transfer". `web/js/autoaim_cmd.js` (not in the integrator list) drives it.
   - **Java (real state exists):** `TeamCode/.../grouped_subsystems/intake_transfer/IntakeTransfer.java` has `Mode {STOPPED, FORWARD, BACKWARD, FEED}`. `forward()` (:38) runs intake AND transfer. `stop()` (:57) stops both. `feed()` (:68) runs both, ignoring full-stop. There is no transfer-only method. `Transfer.java` has `forward()` and `stop()` only.
   - **Conclusion:** Java has no independent transfer state. Transfer is only ever driven together with the intake, or via feed().

2. **Existing command names** (`autos.js:34-48` COMMAND_DEFS; `autoexport.js:27` KNOWN_COMMANDS):
   - intakeOn, intakeOff, shoot, shootAll, aimOn, aimOff, autoAim, setRpm, flowerDeploy, flowerStow, gateOpen, gateClose, park.
   - No transferOn, transferOff, feed, or transfer command exists.
   - Palette (`autoui.js:34-36`) groups: Intake (intakeOn/intakeOff), Shoot, Mechanisms, plus Park.

3. **Command types by file:**
   - `autos.js`: node types follow, wait, waitUntil, command, and groups sequential, parallel, race, deadline. Adapter methods: `intake(on)`, `shoot`, `shootAll`, `aim`, `setRpm`, `flower`, `gate`, `park`, `custom`. Adapter doc (`:15`) has no transfer. `cmdNode` (`:431-451`) maps each command to an adapter call.
   - `autorunner.js`: host bindings at `:179-210`. Command handlers come from `cmdNode` via the adapter. `transfer` is only in the autoAim adapter.
   - `pathing.js:371-379`: an event-preset table with intakeOn, intakeOff, gateOpen, gateClose and Java strings such as `intake.on(); `. Any new command needs a row here too (owner: not integrator).
   - `autoexport.js`: `instantStatements` (`:94-106`) maps intakeOn to `robot.intake.forward();` and intakeOff to `robot.intake.stop();`. It also emits feed-related code for autoAim (`:207-247`, `:330-344`), where `out.transferOn` becomes `robot.intake.feed()` or `robot.intake.stop()`.

4. **Naming mismatch (existing, not introduced by this audit):** `autos.js` `javaCall` strings say `intake.on()` and `intake.off()`. The exporter emits `robot.intake.forward()` and `robot.intake.stop()`. The Java `Intake`/`IntakeTransfer` API has no `on()`/`off()`. Treat the `javaCall` field as documentation only.

## Is a transferOff command sensible?

Yes, as a separate primitive. Today the only way to stop transfer is intakeOff, which also stops the intake. The intake may need to keep pulling balls in while the belt holds them, and nothing in the autos can express that. This is a design judgement, not verified against the robot.

Unverified: whether the real robot wants the intake running while transfer is off. The mechanical behaviour is not in the repo and needs the java lead to confirm.
