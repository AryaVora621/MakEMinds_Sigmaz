## Answer in brief
- The JS scheduler and the default Java export (`statemachine` style) agree on finish, interrupt and empty-group rules for sequential, parallel, race and deadline. One mismatch: empty `deadline()` (see A1).
- Compatible with Pedro: the default export drives Pedro only through `robot.auto.followPath / isBusyOrTimeout / cancelMove / timedOut` (TeamCode AutoDrivebase.java:92, 178, 183, 188). No command library is needed.
- Not compatible as-is: the Ivy/Pedro-commands export. Its dependency is not in the build (see A4).
- Nothing in the repo proves FTCLib, NextFTC or WPILib semantics. Those comparisons are UNVERIFIED (see section 5).

## 1. Per group type (JS = web/js/scheduler.js, Java = web/js/autoexport.js emitStateMachine)

### sequential
- JS: finishes after the last child (scheduler.js:184, 197-199). Child finish ends it with `end(false)`, then starts the next child (194). Zero-length children run in the same tick (183-188).
- Unfinished children on interrupt: only the current child is ended with interrupted=true (197).
- Java: `run` loops children by `_pc` and returns true at the end (autoexport.js:353-355). `cancel` cancels only the child at `_pc` (354). Same as JS.
- Empty: JS finishes at once (184). Java returns true (355, while loop does not run). Match.

### parallel
- JS: finishes when no children are active (`act.length === 0`, scheduler.js:166). Early-finished children are ended normally (`end(false)`, 142). Remaining children are ended interrupted when the group ends (161).
- Java: `run` steps every unflagged child and returns true only when all are flagged (autoexport.js:357-360). `cancel` cancels unflagged children only (359). Match.
- Empty: JS finishes at once (166). Java returns true (360, `all` stays true). Match.

### race
- JS: finishes on the first child finish (`act.length < children.length`, scheduler.js:169). The others are ended with interrupted=true (161). Empty race finishes at once (169).
- Java: first child whose `run` returns true wins; later children are not stepped that tick (`winner < 0 &&`, autoexport.js:363). The others are cancelled (364). Empty race returns true (366). Match.

### deadline
- JS: finishes only when the first argument (the deadline child) finishes (scheduler.js:172-174). Other children that finish early are ended normally and the group keeps running (142, 173). The rest are ended interrupted at group end (161).
- Java: deadline child is `ids[d]`, run first (autoexport.js:378). If it finishes, the others are cancelled and the group returns true (375-378). Other children that finish early are flagged and not re-run (376). Index out of range falls back to 0 (369). Match for non-empty groups.
- Empty deadline: JS `deadline()` gets `cmds = [undefined]` (scheduler.js:171-172). Its initialize throws TypeError inside `startCmd` (c._running on undefined), which the outer try in startCmd catches (25), so the group ends interrupted and calls `ctx.onError` if set. Probe: `deadline:start deadline:interrupt`, done after 1 tick. Java returns true, which is normal completion (autoexport.js:371-372). **Mismatch, see A1.**

### nested groups
- JS: a group's `end` ends its own active children (161, 197, 231). `endCmd` runs children before the group's trace entry (40-42). Nesting works (verified by existing tests tests_js/h_integrator_t08.test.mjs and autos.test.mjs; not re-run here).
- Java: each node gets its own `run<n>` and `cancel<n>` method and state flags (autoexport.js:302, 349-380). Parent calls children by method. Match.

### errors and exceptions
- JS: every command method is wrapped; an exception calls `ctx.onError`, ends the command interrupted and treats it as finished (scheduler.js:19-21, 25, 30, 36, 41). Nothing hangs.
- Java: emitted `run`/`cancel` methods have no try/catch (autoexport.js:306-380). An exception escapes `runOpMode`'s loop; `finally` calls `robot.stop()` (autoexport.js:534). **Behaviour differs from JS, see A2.**

### other JS-only helpers (not emitted by the exporter)
- `repeat` (scheduler.js:202-217) and `conditional` (220-233) are not in the exporter's node set (autoexport.js:7-8). Not part of the Java match. Covered by tests_js/h_integrator_t08.test.mjs (not re-run).

## 2. Java side of the path (what the robot runs by default)
- Default style is `statemachine` (autoexport.js:476). The file has no Ivy import in that case (487-488).
- Root is stepped once per loop, only until finished (autoexport.js:387-391, 529-531).
- `follow` starts `followPath(path, true, FOLLOW_TIMEOUT_S)` once, then polls `isBusyOrTimeout` (306-315). Cancel calls `cancelMove` (315). Pedro methods exist in TeamCode AutoDrivebase.java:92, 110, 178, 183, 188.
- Marker callbacks are polled by chain index and t (autoexport.js:311-313), so no Pedro 2.1.0 chain callbacks are used (matches the domain note).
- A group with two `follow` nodes live at once shares one follower. The exporter warns (autoexport.js:419-439). The JS group itself does not check this.

## 4. Findings
- **A1 (JS vs Java, low):** `deadline()` with no children ends as "interrupt" with a TypeError through onError in JS, but completes normally in Java (autoexport.js:371-372). Fix candidate: in scheduler.js `deadline`, return an immediately-done group when there are no children, same as `race`/`parallel`. Owner: scheduler.js owner. Not verified against the sim's autorunner, which reports onError errors (autorunner.js:332).
- **A2 (Java, medium):** no per-node exception handling in the emitted state machine (autoexport.js:306-380). A bad marker or command throws out of `runOpMode` and ends the OpMode. JS catches it and continues. Java owner or export owner to decide. Not tested on the robot.
- **A3 (JS vs Java, info):** JS `race` and `parallel` add children in list order and step them in that order, like Java. Ordering matches only because of list order; no sort is applied. No mismatch.
- **A4 (Pedro/Ivy, medium):** the Ivy export references a missing dependency and unverified method names (autoexport.js:28, 400-401, 511, 528). Keep `statemachine` as default until fixed.
- **A5 (overlap, info):** scheduler.js `autoAimCmd` has `shootSeconds` default 1.0 (line 103-104), and Java uses `SHOOT_AFTER_MAX_S` (autoexport.js:333, TeamCode). Already listed in docs/overnight/export2.md:21. Not a group-semantics issue.
