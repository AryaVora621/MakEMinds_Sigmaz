# t01 AutoAim blocking semantics audit

Scope: read-only. Files read: `TeamCode/src/main/java/commands/autonomous/AutoAim.java` (154 lines), `AutoAimLogic.java` (146 lines), plus `robot/Robot.java:191-279` and `commands/autonomous/AutoDrivebase.java:123-149` for the update path. No edits, no gradle, no git write.

## Where the blocking loops are
- `AutoAim.java:98-114` main loop: `while (opModeActive.getAsBoolean()) { robot.update(); ... }`
- `AutoAim.java:123-131` shoot-after loop: `while (opModeActive... && now < endS) { robot.update(); robot.feedIfReady(true) ... }`
- Both loops are bounded by time or by `opModeActive`, not by any caller-supplied cancel token.

## Reasons this is unsafe inside a sequential or parallel command group

1. **Double `robot.update()` if the group also updates.** `AutoAim.java:99` and `:124` call `robot.update()` directly. `Robot.update()` (`Robot.java:192`) runs `auto.update()`, limelight, tracker, intake, flower, gate, shooter, and SimBridge publish. If a group scheduler also calls `robot.update()` per loop, every subsystem and the Pedro follower is advanced twice per cycle. The filtered-accel term (`Robot.java:197`) and ball tracker (`Robot.java:203-204`, which uses `setIntakeReversing` before `update()`) assume one call per loop. Double calls distort dt-based code (`AutoDrivebase.java:125` uses `timer.reset()` on each call, so the second call sees dt near 1e-3 and clamps there).

2. **Pedro follower is driven only as a side effect of `robot.update()`.** Follower advancement is `AutoDrivebase.update()` -> `follower.update()` (`AutoDrivebase.java:143`), reached only through `Robot.update()` -> `auto.update()` (`Robot.java:193`). `AutoAim` never touches `follower` directly. Inside a parallel group where AutoAim runs its own blocking loop, a path command that is supposed to run concurrently gets no update unless the group's other branch calls `robot.update()`. A group that runs AutoAim on one branch and a follow command on another will run follower updates only inside AutoAim's loop, so the two branches are not actually concurrent.

3. **Blocks the scheduler thread.** Neither loop returns to a caller until done or timed out. There is no yield per loop. In a command-based scheduler (none exists in TeamCode, see below) this stalls every other command, including the `isBusy` / path-following checks, for up to `timeoutS` plus `SHOOT_AFTER_MAX_S` (`AutoAim.java:122`). The worst case is the sum of both timeouts. The defaults are in `AutoAimTunables`, not read here, so the values are unverified.

4. **No cancel hook.** The only exit besides done or timeout is `opModeActive.getAsBoolean()` (`AutoAim.java:98`, `:123`). There is no `isCancelled` parameter, no `interrupt`, and no `end(interrupted)` hook. A group that wants to preempt AutoAim mid-aim cannot do so. The `perLoop` callback (`AutoAim.java:107-109`, `:128-130`) runs inside the loop, so it can only observe, not stop it. A `perLoop` that throws aborts the loop with the shooter still spinning (`setSpinning(true)` at `:92` is never undone on that path) and the intake still feeding (no `finally`).

5. **No `finally` cleanup.** `robot.intake.stop()` runs at `AutoAim.java:117`, `:132` only on normal exits. If `robot.update()` or `robot.intake.feed()` throws, the intake is left running and the shooter is left spinning. The usage doc (`AutoAim.java:24-26`) relies on the caller's `finally { robot.stop(); }`, which is the OpMode's job, not the group's.

6. **Early-return asymmetry.** `AutoAim.java:89-91` returns false before `setSpinning(true)` if the shooter is null, which is fine. But `AutoAim.java:116-119` returns after `intake.stop()` only when `shootAfter` is false. With `shootAfter` true, a stop from the opMode during the first loop still reaches `:122`, which then runs the shoot-after loop. The loop condition checks `opModeActive` first (`:123`), so it exits at once when the OpMode is stopped. This path is correct, but a group-level cancel does not reach it.

7. **Timing source mixes time bases.** `AutoAim.java:101`, `:122-123` use `System.nanoTime()/1e9`. `AutoAimLogic.update(nowS, ...)` takes that value (`AutoAimLogic.java:81`). Timeout uses `nowS - startS >= effectiveTimeoutS` (`AutoAimLogic.java:117`). This is correct, but it is wall-clock. A group that pauses or pre-empts does not pause the timeout.

8. **Logic is pure, the loop is not.** `AutoAimLogic` is hardware-free and testable (`AutoAimLogic.java:3-6`). `AutoAim.run` is not unit-testable because it calls `robot.update()` and `opModeActive` directly (`AutoAim.java:98-101`). Any group integration test needs a Robot.

9. **Shoot-after loop ignores aim result.** `AutoAim.java:123-131` runs for up to `SHOOT_AFTER_MAX_S` even when `aimed == false` (the timeout case). It keeps calling `feedIfReady(true)`, which itself checks `readyToFire()` (`Robot.java:269`), so nothing is fed unless the shooter is ready. Feeding is therefore gated, but the phase still costs up to `SHOOT_AFTER_MAX_S` of wall time after a failed aim. Whether that is intended is unverified; the class doc (`AutoAim.java:49-53`) says the phase runs regardless.

## Facts checked
- No `SequentialCommandGroup`, `ParallelCommandGroup`, `CommandScheduler`, `InstantCommand` or `LambdaCommand` appears anywhere under `TeamCode/src` (Grep, files_with_matches, no results). So "command group" here is hypothetical. Any group framework used by the team is outside this tree, or not yet built. Unverified whether another repo exists.
- The only caller of `AutoAim.run` in `TeamCode/src` is `commands/autonomous/AutoAimDemoAuto.java:38`, which is a plain LinearOpMode, not a group.
- `TwoPlayerTeleOp.java:125` calls `robot.feedIfReady` directly, so the feed path is also used outside AutoAim.

## Follow-ups for other owners
- Owner of AutoAim: add a `finally` that stops intake and un-spins shooter on any exit, and add a cancel predicate parameter.
- Owner of any group scheduler (not in TeamCode): decide one owner for `robot.update()` per cycle; AutoAim's loops should not call it when run under a group.
- Owner of follower: confirm whether follower updates must run while AutoAim blocks.
