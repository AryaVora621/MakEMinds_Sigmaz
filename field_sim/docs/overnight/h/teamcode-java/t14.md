# t14: Planner export to Pedro Java compatibility

Scope: read-only review of `web/js/autoexport.js` (585 lines), checked against TeamCode Java by grep. Nothing compiled or run (no gradle, no node tests). Pedro 2.1.0 jar not found on disk, so Pedro API claims below are unverified.

## Verdict
Mostly compatible with the statemachine style (default). Pedro calls are plausible, but they are unverified against the 2.1.0 jar. The Ivy style is NOT compatible: its Ivy names are unverified and `autoAim` silently becomes a no-op.

## Pedro calls emitted (statemachine path)
- `follower.pathBuilder()` / `robot.auto.pathBuilder()` (autoexport.js:109, 496). `robot.auto.pathBuilder()` not confirmed in AutoDrivebase.java (unverified).
- `.addPath(new BezierLine(a,b))` / `new BezierCurve(...)` (autoexport.js:118-120, 121). Unverified against Pedro 2.1.0.
- `.setTangentHeadingInterpolation()`, `.setConstantHeadingInterpolation(rad)`, `.setLinearHeadingInterpolation(start,end)` (autoexport.js:123-125). Unverified against Pedro 2.1.0.
- `.setReversed()` no-arg (autoexport.js:126). Unverified: the signature may take a boolean.
- `new Pose(x, y, h)` and `new Pose(x, y)` (autoexport.js:97, 114, 140, 157). Pedro frame (inches, heading rad) matches the rules; the 3-arg constructor is unverified.
- Heading is `Math.toRadians(deg)` (autoexport.js:39-45). Heading is emitted in radians, consistent with the rules.
- Coordinates are emitted raw via `num()` (autoexport.js:8-22). There is no 144 or frame conversion, so the planner must already be in Pedro inches with audience-left origin. This is assumed, not checked here.

## Following and polling
- Follow state calls `robot.auto.followPath(f, true, FOLLOW_TIMEOUT_S)` (autoexport.js:308). `AutoDrivebase.followPath(PathChain, boolean, double)` exists at AutoDrivebase.java:92. Compatible.
- Also used: `isBusyOrTimeout()`, `timedOut()`, `cancelMove()` (autoexport.js:308). Present at AutoDrivebase.java:178, 183, 188.
- Markers are polled, not callbacks (autoexport.js:171-172, 305-306). Calls `robot.auto.getFollower().getChainIndex()` and `getCurrentTValue()`. NO TeamCode file contains these names (grep). The header claims they were verified against `core-2.1.0-sources.jar` (autoexport.js:9-12). That jar was not located here, so this is UNVERIFIED.
- No callbacks are emitted. `addParametricCallback` is never used (autoexport.js:171). Matches the "chain callbacks never fire" fact.
- `callbackMarkers` is imported from `./autos.js` (autoexport.js:14, 20). Not read in this task.

## autoAim: not AutoAim.run
- Generator does NOT call `AutoAim.run`. It uses `AutoAimLogic` per tick (autoexport.js:116-118, 317-332). Rationale in the comment: `AutoAim.run` blocks and would stall sibling branches.
- Real signatures: `AutoAim.run(Robot, BooleanSupplier, boolean)` at AutoAim.java:73, and the 5-arg overload at :87 (blocking).
- Marker form: `startAutoAim(shootAfter)` creates a nested `AutoAimCommand` and steps it with `if (autoAimCmd != null) autoAimCmd.update();` (autoexport.js:186-250, 487). Compatible with the loop, but adds a second entry point.
- Node form (state machine): `new AutoAimLogic(timeout, shootAfter, TRANSFER_ON_START)` (autoexport.js:323-330). Constructor matches AutoAimLogic.java:67. `update(double, boolean, boolean)` returns `Output` (AutoAimLogic.java:81). The `Output` constructor takes (transferOn, done, timedOut, aimed) (AutoAimLogic.java:41), so `transferOn`/`done` fields are consistent.
- Tunables `TIMEOUT_S`, `TRANSFER_ON_START`, `SHOOT_AFTER_MAX_S` exist (AutoAimTunables.java:21, 29, 37).
- Header note says no `AutoAimCommand` class exists yet (autoexport.js:120). The generator nests its own, so there is no clash.
- Robot calls used by the generated code and checked: `robot.feedIfReady(true)` (Robot.java:266), `robot.intake.forward()/feed()` (IntakeTransfer.java:38, 68), `robot.shooter.setSpinning()/ready()` (ShooterBase.java:59, 105), `robot.flower.deploy()/stow()` (FlowerMech.java:65, 70), `robot.gate.open()/close()` (Gate.java:37, 42). All present. `robot.auto` is `AutoDrivebase` (Robot.java:112).

## Command-group framework assumption
- Default style "statemachine" does NOT assume a command framework. It is a hand-rolled per-tick state machine inside `LinearOpMode` (autoexport.js:430-489). Compatible with the current robot code.
- Ivy style DOES assume a framework. It emits `com.pedropathing.ivy.Scheduler.schedule(...)`, `sequential/parallel/race/deadline`, `follow`, `instant`, `waitSeconds`, `waitUntil` (autoexport.js:391-398, 466, 483). Ivy is not a project dependency (autoexport.js:28, 436-443; the header comment says so). Ivy names are marked UNVERIFIED (autoexport.js:452, 466). The `static com.pedropathing.ivy.pedro.PedroCommands.*` import is also unverified (autoexport.js:443).

## Incompatibilities and defects
1. Ivy `autoAim` is a silent no-op: `instant(() -> { })` (autoexport.js:396). The planner's aim is dropped with only a TODO comment.
2. Ivy timed commands `shoot`/`shootAll` become one-shot `instant(() -> robot.feedIfReady(true))` (autoexport.js:397). This does not match the timed semantics; only a TODO comment flags it.
3. Timed command markers (not autoAim) inside a path become a TODO comment only (autoexport.js:256). They run nothing.
4. Ivy `follow()` may need a `Path`, not a `PathChain` (autoexport.js:452, 392). Unverified.
5. Pedro 2.1.0 chain-callback claim is correct per the rules; the export never relies on it (autoexport.js:171). Good.
6. The "verified against core-2.1.0-sources.jar" header (autoexport.js:9-12) cannot be reproduced here. Treat as UNVERIFIED until the jar is located. Gradle dependency is `com.pedropathing:ftc:2.1.0` (build.dependencies.gradle:18).
