## Answers
- Flywheel still spinning after any exit? Yes, in paths 1-8. Only robot.stop() or setSpinning(false) clears it. PID does not advance after exit unless robot.update() runs. Hardware behavior of the last power command: UNVERIFIED (Flywheel.java not read).
- Intake stopped? Yes on paths 1-6 (AutoAim.java:117, :132). Not guaranteed on path 8.
- Turret and hood tracking? They hold the last commanded target and stop moving because nothing calls update(). The hood comment at ShooterBase.java:98 says it only moves inside update(). Robot.stop() stops the turret (ShooterBase.java:178-180) but not the hood.
- The "cancel" case for AutoAim is opModeActive going false, not a command group. A command group cannot interrupt run() except by killing the thread, and no such code exists in these files.

## Is leaving the flywheel spinning on cancel desirable?
- Yes for shootAfter=false. AutoAim.java:48 says so, and the path example (:19-20) keeps calling robot.update(), so the flywheel stays at speed through the next drive.
- Caveat 1: spinning is a sticky flag with no timeout. A cancelled auto that never shoots spins until robot.stop(). Cost is battery and heat (judgment, not measured).
- Caveat 2: shootAfter=true also leaves spinning=true after the shot. Nothing clears it, so the next path keeps spinning unless the caller clears it.
- Caveat 3: if the next step does not call robot.update(), the flywheel freezes at its last power command (UNVERIFIED).
- When the OpMode is ending, leaving it spinning is harmless: the caller's finally robot.stop() clears it (ShooterBase.java:175).

## Cancel-safe wrapper (recommendation, not written)
- Wrap AutoAim.run in try/finally and call robot.intake.stop() in the finally. Do not call shooter.stop() or setSpinning(false) there. That keeps the flywheel for the next path and fixes path 8.
- Decision: keep the flywheel spinning on cancel, and have the caller call setSpinning(false) explicitly before any long non-shooting stretch. Owner: teamcode-java lead for AutoAim.java.
