## Answers

1. **Pure, clock-injected?** Yes. `AutoAimLogic.update(nowS, shooterAvailable, aimReady)` takes time as an argument and touches no hardware (AutoAimLogic.java:81-127). It is a good fit for a non-blocking wrapper: call update() once per loop tick.
2. **Reset/reuse?** Yes. `reset()` clears every field, including `started`, so the next first update re-records the start time (AutoAimLogic.java:132-141). Covered by test (9) in AutoAimLogicTest.java:120-139.
3. **Cancel?** No. There is no cancel method. A wrapper must cancel by calling `reset()` or by dropping the instance. Nothing in the class turns transfer off on cancel, so the wrapper must stop the intake itself.
4. **shootAfter phase?** Not in AutoAimLogic. `shootAfter` only changes what happens after `done` (AutoAimLogic.java:90-96). The bounded second loop lives in AutoAim.run (AutoAim.java:116-133).
5. **Gap for a wrapper?** Yes. The second loop is a real gap a command wrapper must reimplement:
   - It is a wall-clock loop on `System.nanoTime()` with `SHOOT_AFTER_MAX_S` (AutoAim.java:122-123). It does not use the logic's clock.
   - It feeds through `robot.feedIfReady(true)` (AutoAim.java:125), not `robot.intake.feed()`, which the first loop uses (AutoAim.java:103). I did not check what `feedIfReady` does, so that difference is unverified.
   - It ignores `AutoAimLogic` after `done`, so `transferOn` is never read in this phase.
   - It runs `perLoop` (AutoAim.java:128-130).
6. **Other mismatches between AutoAim.run and AutoAimLogic:**
   - Timeout clamp: `run()` maps `timeoutS <= 0` or NaN to `AutoAimTunables.TIMEOUT_S` (AutoAim.java:94). The logic's zero/NaN-to-0 rule (AutoAimLogic.java:116) is therefore never reached through `run()`. Test (6) and (6b) exercise it only at the class level.
   - Shooter-unavailable branch: `run()` passes `shooterAvailable = true` always (AutoAim.java:101) and returns false early when `robot.shooter == null` (AutoAim.java:89). So the logic's no-shooter branch is dead code on the `run()` path. `statusText`'s "no shooter" text is also unreachable from `run()`.
   - Wall clock: `run()` uses `System.nanoTime()` directly. The injected clock exists only in the logic and is not used in `run()`.
   - Telemetry: `run()` never exposes the `Output` to callers, so `statusText` is not wired into `run()`. Callers outside AutoAim.java were not checked (the grep was truncated).
7. **Labels.** Callers of AutoAim.run outside AutoAim.java were not confirmed. The test comment that AutoAim has no static fields (AutoAimStatusTextTest.java:10-11) was not verified against AutoAim.java.

## Test gaps (not covered by the current tests)

Logic-level:
- A. The `transferOn` value on the done or timeout update itself. Test (4) checks done, timedOut and aimed on the timeout update, but not transferOn. The timeout path does not set transferOn (AutoAimLogic.java:117-123), so it carries the previous value.
- B. Timeout with shootAfter=true. Test (8) covers only the aimed path. The timeout path with shootAfter=true has no test.
- C. Timeout with shootAfter=false, transfer off on the next update. Test (7) covers only the aimed path.
- D. transferOnStart=false with timeout: transfer must stay off. No test.
- E. transferOnStart=false with shootAfter=true: transfer on after aimReady and kept on. No test.
- F. Boundary tie: aimReady true at exactly elapsed == timeoutS. Code checks aimReady first, so this should be aimed, not timed out. No test.
- G. shooterAvailable=false after alignment has started (mid-run), and shooterAvailable=false with aimReady=true. The code checks the shooter first (AutoAimLogic.java:98), so aimed should be false. No test.
- H. reset() called mid-run after done, and reset() with shootAfter=true.
- I. Non-finite time inputs. If nowS is NaN, `nowS - startS >= timeout` is false, so the command never times out. If timeoutS is +Infinity, it never times out. Neither is tested or guarded. Whether FTC Dashboard can set TIMEOUT_S to Infinity is unverified.
- J. Calls after the shootAfter=false turn-off update. Test (7) checks one update only; later updates staying off is not asserted.

Status text (AutoAimStatusTextTest.java):
- K. No exact-string test for "AutoAim: no shooter (not aimed)" or "AutoAim: aligning". Only `contains` checks exist, and the no-shooter test is built from logic output, not constructed directly.
- L. AutoAimStatusTextTest.java:66-67 is weak. `assertFalse(text, text.contains("aimed") && !text.contains("not aimed"))` passes for "AutoAim: no shooter (not aimed)" for the wrong reason, because the text contains "not aimed".

AutoAim.run level (no test file for run found in this review):
- M. No JUnit test exercises AutoAim.run or the shoot-after loop. Robot and the OpMode clock make this hard to unit-test without a seam. Unverified whether a test seam exists.

## Suggested seams (for the lead to decide; not edited here)

- Inject a `DoubleSupplier` clock into AutoAim.run and the shoot-after loop, so the bounded phase can be tested.
- Move the shoot-after decision into AutoAimLogic as an explicit phase, or give the wrapper a `phase()` accessor.
- Clamp `nowS` and `timeoutS` so non-finite values fail safe (timeout to 0 on NaN now, and clamp Infinity to a finite max).
