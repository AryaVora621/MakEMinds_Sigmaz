# t09 Flower mechanism Java logic audit (read-only; nothing edited, no gradle, no git)

Files read: TeamCode/src/main/java/commands/subsystems/flower_mech/FlowerMech.java, FlowerMechLogic.java; TeamCode/src/test/java/commands/subsystems/flower_mech/FlowerMechLogicTest.java; robot/Robot.java:296-312 (toggleFlower). Also grepped for USE_FLOWER_MECH / ball-count symbols.

## What the Java does
- Hardware: two Axon servos in sync, B mirrored (FlowerMech.java:20 SERVO_B_REVERSED). Command = progress p in [0,1] mapped to A and B degrees (FlowerMech.java:126-129).
- States (FlowerMechLogic.java:8): STOWED -> DEPLOYING -> DWELL -> STOWING -> STOWED, plus FAULTED.
- deploy() only from STOWED (FlowerMechLogic.java:34-39). stow() cancels DEPLOYING or DWELL, ignored in FAULTED/STOWED (:42-47).
- Transitions: DEPLOYING -> DWELL when progress==goal and arrived (or untrusted) (:117-123). DWELL -> STOWING after DWELL_MS (:125-130). STOWING -> STOWED when reached (:132-133).
- Slew: progress moves at SLEW_DEG_PER_S / spanDeg per second (:109-115). SLEW 0 jumps to goal.
- FAULTED is latched. Stall or sync divergence (> SYNC_TOL_DEG for > SYNC_FAULT_MS) faults only while moving, with trusted feedback, and outside grace (:89-104). FAULTED returns NaN, so servos hold their last commanded target (FlowerMech.java:94-95).
- clearFault() (FlowerMech.java:79-83, logic :54-62) goes to STOWING with FAULT_GRACE_S of no re-latch.
- Blocking: none. update() is a non-blocking per-loop state machine (FlowerMech.java:85-96). dt is capped at MAX_DT_S. Deploy-dwell-stow runs on its own timer after one deploy() call, with no operator input needed.
- Robot wiring: Robot.java:150 constructs it only if USE_FLOWER_MECH (default false, :104). update() each loop (:211-212). toggleFlower (:303-311) clears a fault if faulted, otherwise toggles. TwoPlayerTeleOp.java:89 binds X to it (rising edge).

## Ball count interaction
- None in code. FlowerMech, FlowerMechLogic and Robot.toggleFlower never read or write any ball, pollen or hold count (grep for ballCount / holdCount / ballsHeld / pollen in TeamCode/src/main/java returns no flower coupling). Only FieldConstants.java:110-112 mentions pollen counts (hold limit 4; hive tips at 8, [USER-CONFIRMED] label).
- So "the flower empties the flowers" (FlowerMech.java:9) is a physical intent only. Nothing in Java models or gates dumping pollen, and no hold count changes on deploy.
- Consequence: the Java cannot tell whether a dump happened. The driver would need to see it.

## Test gaps (FlowerMechLogicTest.java)
Covered: full cycle, cancel while DEPLOYING, stall while stowed or dwelling (no fault), stall while moving trusted (fault), sync timer, untrusted open loop, grace window, dt cap, stale stall on first update, persistent stall.
Not covered:
1. Stall while STOWING (logic allows it, :89 isMoving includes STOWING). Could fault on the way back, untested.
2. stow() during DWELL (the advertised cancel path) and cancel from DWELL specifically.
3. stow() and deploy() no-ops when FAULTED, and clearFault() when not faulted (no-op).
4. Sync divergence that recovers before SYNC_FAULT_MS (syncBad reset at :98-99). Only the fault path is tested.
5. slewDegPerS = 0 (jump-to-goal path, :109-110).
6. isDeployed(trusted, atTarget) return values, and the progress==goal gate.
7. FlowerMech.java itself: no test. Constructor with ENABLED false, SERVO_COUNT 1 (b == null), syncDiff NaN paths, command(0) in ctor, toggle() and clearFault() at class level. Needs a HardwareMap stub or a refactor to test.
8. Robot.toggleFlower() has no test (fault-clear-vs-toggle branch, null flower).
9. Fault mid-cycle to recovery, end to end: clearFault -> STOWED -> deploy again.
10. No test that a fault leaves servos at last target (NaN path is only checked on the logic side).
11. No test that stall while trusted=false during STOWING/DEPLOYING is ignored (partly covered by untrustedFeedback test).
