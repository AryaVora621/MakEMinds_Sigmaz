# t12 Gate/Transfer/Intake command-safety audit

Scope: read-only audit. Ran Read and Grep only. No gradle, no git writes, nothing compiled or run on robot or sim. Only this file was written.

## 1. Per-loop safety (can a non-blocking command call it every loop?)
- Intake.forward/backward/stop/setPower: Intake.java:21-36. Idempotent motor power write, no timing. SAFE.
- Transfer.forward/backward/stop/setPower: Transfer.java:21-36. Same shape. SAFE.
- IntakeTransfer.forward(): IntakeTransfer.java:38-48. Calls endFeed() (:39), so it cancels a feed() latched earlier. Halts both motors while full-stop applies (:41-45). SAFE only if no feed() in the same loop.
- IntakeTransfer.backward()/stop(): :50-62. Cancel feed, never full-stop gated. SAFE.
- IntakeTransfer.feed(): :68-73. Idempotent (javadoc :65 says safe every loop) but LATCHED: runs until stop/forward/backward. No timeout. Bypasses full-stop by design.
- IntakeTransfer.resetFullStop(): :98-105. Clears latch and override; restarts motors if mode is FORWARD. Driver-button use only.
- IntakeTransfer.update(tracker): :80-88. Must be called only by Robot.update (Robot.java:205).
- Robot.feedIfReady(wantFire): Robot.java:266-279. Per-call decision, safe every loop. Returns false, so the caller must command intake itself (TwoPlayerTeleOp.java:125-133, AutoAim.java:125-126).
- Robot.toggleFlower(): Robot.java:303-312. TOGGLE plus clearFault when faulted. NOT every-loop safe.
- Robot.toggleGate() and Gate.toggle(): Robot.java:331-335, Gate.java:47-49. TOGGLE on commanded state (open flag, not measured). NOT every-loop safe.
- Gate.open()/close(): Gate.java:37-45. Set target only (servo.setTargetDeg). SAFE every loop. Motion runs in Gate.update() (:51-55), called from Robot.update (Robot.java:214-216).
- FlowerMech.toggle(): FlowerMech.java:74-76. Deploys only from STOWED; in any other state it calls stow(), so it cancels mid-cycle. NOT every-loop safe.
- FlowerMech.deploy()/stow(): FlowerMech.java:65-72. Delegate to FlowerMechLogic, which was NOT read. UNVERIFIED whether deploy() during DEPLOYING/DWELL restarts the cycle.
- FlowerMech.update(): FlowerMech.java:85-96. Non-blocking timed sequence (dtTimer, logic.update). Must run every loop (Robot.java:211-213).
- FlowerMech.clearFault(): FlowerMech.java:79-83. One-shot, FAULT_GRACE_S window.

## 2. Blocking and sleep hazards (grep results)
- Thread.sleep / sleep(: no matches under TeamCode/src/main.
- Subsystem files Intake, Transfer, Gate, GateLogic, IntakeTransfer, FlowerMech, AxonServo contain no loops or waits. AxonServo timing is nanoTime-based (AxonServo.java:149-201).
- Blocking loops in commands (they call robot.update() themselves and block other work):
  - AutoAim.java:98-114: aim phase, calls intake.feed()/stop() (:103-105).
  - AutoAim.java:123-131: shoot-after phase, bounded by SHOOT_AFTER_MAX_S.
  - ShootWhileDrivingDemoAuto.java:75 and ProfileDemoAuto.java:111: timed waits (`seconds()` comparisons).
  - ShootWhileDrivingDemoAuto.java:61, ProfileDemoAuto.java:62 and :84: opmode loops.
- Gap: Robot.stop() (Robot.java:428-442) stops drivebase, intake, shooter and limelight, but not gate or flower.

## 3. Hazards (ranked)
- H1 Latched feed. IntakeTransfer.java:68-73 has no timeout. A command that exits without stop/forward/backward leaves intake and transfer running. Current callers end with a stop (AutoAim.java:117,132; ShootWhileDrivingDemoAuto.java:94; TwoPlayerTeleOp.java:131). Any new command needs try/finally.
- H2 Last writer wins on intake. No owner or lock on Intake/Transfer. Any loop that calls feedIfReady(true) and then intake.forward()/stop() gets the later call. TwoPlayerTeleOp avoids this only with its else branch (:125-133).
- H3 forward()/backward() cancel feed(). IntakeTransfer.java:39 and :51. Two commands that alternate feed and forward flicker the intake.
- H4 FlowerMech.update() not called (for example, a command bypasses Robot.update) leaves servos at the last target and the sequence frozen. Robot.java:211-213.
- H5 Feed path bypasses readiness. AutoAim.java:103 calls feed() on out.transferOn without readyToFire() (Robot.java:254-259). Intent unverified (AutoAimLogic not read).
- H6 Gate toggle versus set. Gate.toggle() reads commanded state (Gate.java:47-49). Mixing toggle with open()/close() from two commands makes the result order-dependent.
- H7 Flower toggle cancels mid-cycle (FlowerMech.java:74-76). Robot.toggleFlower also clears a fault instead of deploying (Robot.java:307-310), so one press may do no deploy.
- H8 Full-stop latch can lock the intake. IntakeTransfer.java:12-17 and :98-105. Without the shooter sensor the count never drops, so only resetBallCount()/resetFullStop() recovers (Robot.java:318-323).
- H9 Doc defect: Robot.java:325-326 has a dangling javadoc "Toggles the gate (null-safe)." above the toggleFarCellUp javadoc.

## 4. Conflict matrix for two parallel commands
- intake: CONFLICT. Writers are IntakeTransfer forward/backward/stop/feed (IntakeTransfer.java:38-73). Callers: OnePlayerTeleOp.java:51-60, TwoPlayerTeleOp.java:125-133, AutoAim.java:103-126, ShootWhileDrivingDemoAuto.java:91-94. Needs one owner.
- transfer: CONFLICT, same as intake. Transfer is only reached through IntakeTransfer. Requirement: same requirement as intake.
- shooter: CONFLICT by design. Robot.update calls shooter.update every loop (Robot.java:217-220). The shooter's setters were NOT audited (ShooterBase not read). Feed gating reads shooter.ready() (Robot.java:255). Only one owner should set targets.
- gate: CONFLICT on toggle versus open/close (H6). Otherwise read-only to other code (Robot.java:244, 333).
- flower: CONFLICT between toggleFlower and deploy()/stow() from a second command. Re-entry behaviour unverified (H7, FlowerMechLogic not read).
- Intake/transfer do not share hardware with gate or flower, so those pairs are independent.
- Suggested requirements: one IntakeTransfer requirement (intake + transfer), one shooter requirement, one gate requirement, one flower requirement. A feed command requires IntakeTransfer and shooter.
