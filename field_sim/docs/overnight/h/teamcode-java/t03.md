# t03: Command interface existence survey (teamcode-java)

Scope: read-only grep and read of TeamCode/src, build.gradle, build.common.gradle, build.dependencies.gradle, TeamCode/build.gradle, libs/. No gradle, no git writes, no edits outside this file.

## Verdict
There is no command framework in the Java code. No NextFTC, FTCLib, SolversLib, SequentialCommandGroup, ParallelCommandGroup, or homemade Command/Subsystem interface exists. Lifecycle is ad hoc: each class exposes its own `update()` called by `robot/Robot.update()`. The `commands` package is a plain directory/package name with no framework behind it.

## Is a framework-free minimal interface the right wrapper?
Recommendation: yes, add a small in-repo interface, for example `commands/core/Command.java`:
`void start(); void update(); boolean isFinished(); void end(boolean interrupted);`
Reasons:
- Nothing to link against. The gradle deps list (build.dependencies.gradle:8-19) has no command library, and libs/ is empty of jars. Adding NextFTC, FTCLib, or SolversLib would be a new external dependency. Its version and availability are unverified here.
- It can wrap existing `update()` methods without rewriting subsystems. Robot.update() stays the single driver.
- It matches the existing MotionProfile lifecycle (start then per-loop call), so the pattern is already familiar to this codebase.
- Sequencing (sequential and parallel groups) can be a small homemade class on top of the interface. This is an assumption, not tested.

Caveats (unverified):
- Whether Pedro 2.1.0 ships its own command classes is unverified. The jar is not in the repo, and the Pedro chain callbacks are known not to fire (per OVERNIGHT_RULES.md), so do not depend on Pedro for sequencing.
- I did not search FtcRobotController/ or the Pedro jar contents.
