# t15: autoAim JS command model vs Java AutoAim.run

Scope: read-only review. No files edited besides this report. No git writes, no gradle.

## Answer
No. The JS model (web/js/autoaim_cmd.js) matches Java on the basic loop (aim until ready or timeout, transfer on at start, flywheel left spinning when shootAfter is false). It differs on the timeout default, the shoot-after bound and early exit, whether a timeout still fires, how firing works, and the readiness definition.

## Mismatches (ranked by impact)
1. Shoot-after after a timeout. JS fires only if fireOnTimeout is set (autoaim_cmd.js:196; default false at :74). Java always enters the shoot phase after the aim loop, whether or not aimed (AutoAim.java:116-131), and feeds whenever Robot.readyToFire() allows (Robot.java:254-270, feed at AutoAim.java:125). The exporter does the same (autoexport.js:326, feed block runs after out.done, which is also set on timeout). A shot that becomes ready late fires on the robot but not in the sim.
2. Firing mechanism. JS calls host.shoot({all:true}) once on ready and ends on hopperEmpty (autoaim_cmd.js:116-121, :162). Java and the exporter never call a shoot-all; they feed ball by ball, gated by readyToFire. Java also ignores hopper state and runs the full 5 s (AutoAim.java:123).
3. Shoot-after duration. JS 6 s cap (autoaim_cmd.js:39, asserted at tests_js/autoaim_cmd.test.mjs:189) vs Java 5 s (AutoAimTunables.java:37, AutoAim.java:122).
4. Readiness definition. JS requires 0.1 s of continuous readiness (settleSec). Java uses shooter.ready() instantly (AutoAim.java:100). Java's ready also has a hood timeout: after HOOD_READY_TIMEOUT_S (ShooterBase.java:31, placeholder 1.5 s) it can report ready with the hood not at target (ShooterBase.java:42 doc). JS has no hood timeout, so the two can disagree when the hood is slow.
5. Timeout default not reachable from the planner. The runner reads args.timeout (autorunner.js:212), defaulting to 4 s. The palette args expose only shootAfter (tests_js/auto_list.test.mjs:255), and autos.js:442 passes only args. So the sim always uses 4 s, while the robot uses 3.0 s. The exporter reads node.args.seconds, falling back to TIMEOUT_S (autoexport.js:321). Neither the sim nor the palette can set seconds, so the exporter's seconds path is not reachable from the UI.
6. Transfer policy. Java can hold transfer off until aligned (TRANSFER_ON_START=false). JS always turns transfer on at start (autoaim_cmd.js:148). No JS option exists.
7. Track and keepAim. Sim-only (autoaim_cmd.js:64; autorunner.js:217-222). AutoAim.run has no track mode and is blocking. The exporter is non-blocking but has no tracking after done.
8. No-shooter path. Java returns false silently (AutoAim.java:89-91). JS warns and completes (autorunner.js:189). Behavior is the same (command completes), but the sim reports a warning.
9. Third model. web/js/scheduler.js:103 autoAimCmd uses shootSeconds default 1.0 and a ready callback. It is a separate model with a 1.0 s fire window, unlike both the 6 s JS model and the 5 s Java value. Its tests are in tests_js/scheduler_autoaim.test.mjs. Which one the sim uses for export is unverified.

## Things that match
- Timeout check uses elapsed >= timeout in both (AutoAimLogic: nowS - startS >= timeout; JS: elapsed >= timeout - 1e-9).
- A non-positive timeout falls back to the default in Java (AutoAim.java:94). JS treats a missing timeout as the default (autoaim_cmd.js:78).
- Flywheel left spinning: Java sets setSpinning(true) (AutoAim.java:92) and never clears it. JS does not cut rpm; stop() only sends transfer(false) (autoaim_cmd.js:213). Matches in intent.
- Intake stopped on exit with shootAfter false: Java (AutoAim.java:116-117) and JS (stop, autoaim_cmd.js:213).

## Test gaps
- Constant parity is only partly tested. tests_js/h_teamcode-java_t16.test.mjs already flags the TIMEOUT_S mismatch (3.0 vs 4) as FAILING BY DESIGN and documents the 5 vs 6 s shoot bound, with no assertion.
- No test covers timeout plus shootAfter at the runner level. autoaim_cmd.test.mjs:203-218 is unit only.
- No test for TRANSFER_ON_START=false (JS has no such option, so nothing to test yet).
- No test that the flywheel holds the target rpm after shootAfter=false completes.
- No test for the hood-timeout readiness path (JS has none to test).
- The runner-level timeout case (autoaim_run.test.mjs:63) uses args.timeout, which the palette cannot set, so the planner-reachable path is untested.
- Java side not checked: AutoAimLogicTest.java exists; I did not confirm whether AutoAim.run's bounded shoot loop has any test.
