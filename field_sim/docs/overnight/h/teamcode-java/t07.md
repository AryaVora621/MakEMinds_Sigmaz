# t07: Java vs JS hold-limit parity (5th ball at intake, 4 held)

Scope: read-only. I ran no tests, no gradle, no git writes. Every claim below is from reading the cited lines.

## Constants
- Java: `MAX_BALLS = 4` (BallTracker.java:12), clamped to >= 1 (BallTracker.java:28).
- JS: `MAX_HELD = 4` (balls.js:90). Comment says it matches matchrules RULES.holdLimit (balls.js:87-89).
- matchrules.js: `holdLimit: 4` (matchrules.js:9). balls.js does NOT import matchrules (balls.js:91-92 imports only hivemesh.js and hivetip_model.js), so the two 4s are separate hardcoded constants.

## Scenario: 4 balls held, a 5th ball rolls into the intake

### Java (TeamCode)
1. Intake motor is not gated by default. `AUTO_STOP_WHEN_FULL = false` (IntakeTransfer.java:18). Full-stop is only applied via `shouldRunForward` (IntakeTransfer.java:139-141) and `modeMayRun` (IntakeTransfer.java:144-146), and only when `shooterSensorUsable()` is true (IntakeTransfer.java:132-134).
2. Robot.java:161-162 sets the full-stop from a `fullStop` value. I did not verify that value's default, so whether full-stop is on in the real robot is UNVERIFIED.
3. If full-stop is off, the intake keeps running, so the 5th ball is physically taken in. The tracker sees an intake rising edge: `counter.increment()` (BallTrackerLogic.java:67-68) calls `set(count+1)`, which clamps to max (BallCounter.java:25-27, 34-35, 45-47). Count stays at 4.
4. The intake event still increments `intakeEvents` (BallTrackerLogic.java:69, cap max+2 at line 55). So `consumeIntakeEvent()` returns true for the 5th ball. Nothing in TeamCode calls `consumeIntakeEvent()` (grep: only BallTracker.java:88-93 defines it). The event is unused today.
5. Outcome: ACCEPT (physically), COUNT SATURATES AT 4. No refusal, no reject, no eject. Nothing ejects automatically. `backward()` is manual only (IntakeTransfer.java:50-55).
6. Drift: physical = 5, count = 4. On the next shot, the shooter falling edge decrements the count to 3 (BallTrackerLogic.java:88-93). Physical is still 4, so `isFull()` (BallCounter.java:41-43) reads false and the intake keeps pulling. Each over-capacity ball makes the count underreport. This is a real mismatch.
7. If full-stop is on and the shooter sensor works: IntakeTransfer.update() (IntakeTransfer.java:80-87) sets `full = tracker.isFull()` and stops forward intake and transfer. The 5th ball is still partly pulled in before the stop lands, so the stop is not a hard refuse. Note: a fresh update() must run after the 4th ball is counted.

### JS (field_sim)
1. Refusal is enforced inside the intake step, before any pull or load: `if (I.space <= 0 || this.held.length >= MAX_HELD) break;` (balls.js:582). This check is independent of the app's ammo toggle.
2. The 5th ball is not loaded and not pulled (the break is before the pull at balls.js:603-606). It stays free on the floor and bounces off the robot body through `_robotCollide` (balls.js:665-690). Outcome: REFUSE. No eject, no event.
3. `onIntake` only fires on load (balls.js:462, load at balls.js:596-599), so the refused ball produces no intake event. app.js:432 therefore does not increment the ammo counter for it.
4. When a slot frees (fireHeld dequeues the oldest held ball, balls.js:326-335, called from app.js:426), a ball still sitting at the mouth can be loaded on a later substep. So the JS refused ball is retried, not lost.
5. App wiring: `S_PRACTICE.ammoLimit` defaults to false (app.js:295). Then `space` is Infinity (app.js:449). The MAX_HELD check still caps the hold at 4.
6. Shots free a slot only through `fireHeld` (app.js:426). `S_PRACTICE.ammo--` (app.js:428) runs only when ammoLimit is on. The ammo display counter can therefore drift from the real hold list (balls.js:249 `held`) when ammoLimit is off. It is display-only, not a gate.

## Mismatch summary
| # | Topic | Java | JS | Severity |
|---|-------|------|----|----------|
| M1 | 5th ball at 4 held | Physically accepted; count clamped at 4 (BallTrackerLogic.java:67-68, BallCounter.java:34-35) | Refused, not loaded (balls.js:582) | HIGH: behavior differs |
| M2 | Count after 5th ball and a shot | Undercounts by 1 (4 -> 3 while 4 physical) (BallTrackerLogic.java:88-93) | Hold list stays exact (balls.js:598, 326) | HIGH: count drift |
| M3 | Intake default gate | Off (IntakeTransfer.java:18) and needs shooter sensor (line 133) | Always on (balls.js:582, no toggle) | HIGH |
| M4 | Intake event for refused ball | Event fires (BallTrackerLogic.java:69), unused today | No event (balls.js:462) | LOW |
| M5 | Cap constant source | Java MAX_BALLS, hardcoded 4 (BallTracker.java:12) | balls.js MAX_HELD=4 and matchrules.js holdLimit=4 are separate, not linked | LOW (drift risk) |
| M6 | Ball retained vs lost at full | Java: already inside the robot (no retention issue beyond the count) | JS: ball stays at the mouth and loads when a slot frees | info |

## Decisions and recommendations (not applied; I edited no code)
- Java: enable a hard full-stop by default, or add a count-independent guard. A physical 5th ball cannot be stopped by counting alone, so the stop needs sensor-based detection or a mechanical limit. Owner: java lead.
- Java: `BallCounter.set` clamps silently (BallCounter.java:34-35). Consider logging an over-capacity event so drift is visible. Owner: java lead.
- Java: either wire `consumeIntakeEvent()` or remove it. Owner: java lead.
- JS: export holdLimit from matchrules.js and import it in balls.js, so the two constants cannot drift. Owner: field_sim physics owner (not me).
