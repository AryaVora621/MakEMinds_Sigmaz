## Findings per check
1. **Hinge sign: correct.** `hinge.rotation.y = -deg` gives +x -> (cos deg, 0, sin deg) for negative deg, so the arm drops forward. Matches `tipRobot` z = h.z + L sin(a). Verified numerically.
2. **Wrist counter-rotation: correct.** `wrist.rotation.y = +deg` cancels the hinge, so the paddle hangs straight down (dot -1.000) at all angles. The real 4-bar linkage is not modelled (the code comment says so); the 3D is an ideal counter-rotation.
3. **Paddle bottom z: matches.** 3D rubber bottom equals `tipRobot` z to 0.000 at all angles. The 3D bottom is `wrist.z - (height + rubberThickness - 0.4)`, which equals the logic `drop`.
4. **Rear mirroring: consistent.** `rotation.z = PI` plus `position.x = -H.x` gives tip x = -(H.x + L cos a) and z unchanged, which matches `sign = -1` in logic. Verified numerically. Feed alignment (`flowerarm.js` L90, `+PI` for sign<0) and intake mouth (`m.x * sign`) use the same convention, read only.
5. **JSON vs JS mirror: match.** `flower_arm.json` hinge, arm, angles and paddle equal `DEFAULT_ARM_CFG`.
6. **Group visibility with CAD: code path looks right, not exercised.** `web/data/robot.glb` is NOT present (`web/data` listing), so the CAD branch in `app.js` L250-256 has never run here. By reading: `robotmodel` hides all `robot.children` when the GLB loads, then `app.js` L255 sets `built.parts.flowerArm.group.visible = true`. `parts.flowerArm` is the object returned by `buildFlowerArm`, so `.group` is correct. `buildFlowerArm` defaults to `visible = true`. Not confirmed in a browser.

## Issues and risks (no edits made)
- **Hardcoded 0.4 offset in two files, not in the JSON.** `flowerarm.js` L67 (`drop = P.height + P.rubberThickness - 0.4`) and `flowerarm3d.js` L58-59 (paddle/rubber local z offsets `+0.4`). The two agree today. If one is changed alone, tip and model drift apart silently. Suggest moving 0.4 into `paddle` in the JSON (owner: flower-mech logic and 3D owner, or lead).
- **Arm position vs CAD frame is unverified.** The hinge (8.0, 0, 9.2) and the arm are placeholders (`prov: placeholder` in the JSON). Nothing in the repo checks them against `robot.glb`. Once a GLB exists, the hinge must be placed from CAD. TODO, not invented.
- **Tip is paddle centre x=0 only.** The contact model uses one tip point. The paddle is 8 in wide (y), so balls near the side edges are not represented by the tip. Logic and 3D both use y = 0, so they agree. Modelling limitation, not a mismatch.
- **Tests not run.** `tests_js/flowerarm.test.mjs` exists; I did not run `node --test`. My numbers come only from the ad hoc script above.

## Verdict
The 3D arm and the logic `tipRobot` agree to numerical precision for front and rear, at 7 angles from +90 to -50 deg. Hinge sign, wrist counter-rotation and rear mirroring are all correct. Open items: the duplicated 0.4 offset, the placeholder hinge against an absent CAD, and the CAD visibility path not run in a browser.
