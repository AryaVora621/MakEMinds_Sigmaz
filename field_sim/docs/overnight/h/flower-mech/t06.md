# t06: feedFromFlower hold-limit audit

Lead: flower-mech. Scope: read-only audit plus headless repro. No product files edited.

## Hopper cap wiring (read: web/js/app.js:1070, 295, 428, 432, 449)
- `feedFromFlower(..., { count: S_PRACTICE.ammo, cap: S_PRACTICE.ammoLimit ? S_PRACTICE.ammoCap : 99 }, fp)`
- Defaults: `S_PRACTICE.ammoCap = RULES.holdLimit = 4` (app.js:295, matchrules.js:9). `ammoLimit = false` (app.js:295, checkbox `#opt-ammo` unchecked in index.html:144).
- So by default the feed cap is **99**, not 4. The 4 limit only applies when "Limited balls" is checked.
- `S_PRACTICE.ammo` is incremented in `world.onIntake` (app.js:432) for every intake, pollen and nectar alike. It is decremented only in `shoot()` and only when `ammoLimit` is on (app.js:428). It is set to `min(4, cap)` on match start and on auto start (app.js:617, 706). Nothing else touches it.

## Where the real 4 limit lives (read: web/js/balls.js:90, 582, 598; flowerarm.js:104-127)
- `MAX_HELD = 4` (balls.js:90). The intake refuses when `this.held.length >= MAX_HELD` (balls.js:582). This check runs whether or not Limited balls is on.
- `feedFromFlower` never reads `world.held`. It reads only `hopper.count` and `arm._pending`. It never pushes into `world.held` directly, so the only path into the hold is the intake.
- Pending: entries drop when `ball.state !== 'free'`, when the ball leaves `world.balls`, or after `pendingTimeoutS` = 1.5 s (flowerarm.js:106). Released balls are `free` while in flight, so they count toward the cap check until the intake takes them.
- Nectar: the feed only releases pollen (flowerarm.js:113). The hold FIFO and `ammo` both count nectar as 1 each. The feed's check therefore counts nectar too, which is conservative.

## Answers
1. **Can the feed push the robot past 4?** Not in the sim. Every ball that enters the hold goes through the intake's `MAX_HELD` check, and no run reached FIFO > 4 (maxHeld = 4 in all cases). The flower never adds to the hold directly.
2. **But it releases into a full robot.** With Limited balls OFF (the default), the feed cap is 99. Case K releases up to 4 balls per deploy while the hold is already 4. Those balls stay free on the floor. This is not a hold overflow, but the feed ignores the real hold and wastes balls.
3. **Pending and intake together.** The intake's `space` is `cap - ammo` and ignores pending. The feed's check is `ammo + pending < cap`. The real stop is still `MAX_HELD`, so no overflow was seen. In run A/B/D/G, `ammo + pending` reached 5 for one frame. That is a bookkeeping artifact: the ball captured this frame stays in `_pending` until the next feed call. It is not a real overflow (held max stayed 4).
4. **Nectar vs pollen.** Both count toward `ammo` and the FIFO. The feed only releases pollen, so nectar in the hold reduces feed capacity. That is correct, if conservative.

## Defects found (for owners, not fixed here)
- **D1 (app.js:428):** shoot decrements `ammo` only when Limited balls is on. With it off, `ammo` drifts above the real hold (case E: ammo 4, held 0). Turning Limited balls on afterward gives intake space 0 and blocks both intake and feed until 4 shots. Suggest decrementing `ammo` on every shot, or deriving `ammo` from `world.held.length`.
- **D2 (app.js:617, 706):** the match preload sets `ammo = 4` but does not seed `world.held`. Case C shows intake and feed both blocked with no real balls held. This may match a physically full preload, but the sim should seed the FIFO so the state is consistent. Owner decision.
- **D3 (flowerarm.js:110 via app.js:1070):** the feed should cap on the real hold, e.g. `min(cap, MAX_HELD - held.length)`, regardless of Limited balls. Without that, the default mode feeds into a full robot (case K).
