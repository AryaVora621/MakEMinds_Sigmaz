# t07: flower double-feed and pending audit (read-only)

Verdict: YES, a ball released by the flower can be released again. The pending list does not stop it. `fedCount` and `_pending` both over-count. Confirmed in a fake world and against the real `BallWorld`.

## Code read
- `web/js/flowerarm.js:97-102` `inVolume(b, fl, margin)`: xy uses the bbox plus margin, z is `b.z >= 0 && b.z <= zr[1] + b.r`. The lower z bound is 0, not `scoring_volume_z[0]` (4.25 in for flower 1). Balls resting on the floor inside the xy footprint count as "in volume".
- `flowerarm.js:106` pending filter: keeps an entry while `age < pendingTimeoutS (1.5)`, `ball.state === 'free'` and `world.balls.includes(ball)`. It never dedupes and never removes a ball that is already in flight.
- `flowerarm.js:110` cap: `fedCount >= maxBallsPerDeploy (4)` or `hopper.count + _pending.length >= hopper.cap`. Duplicate pending entries inflate the second term.
- `flowerarm.js:113` top selection: iterates all `world.balls`, skips only `scored` and non-pollen, and filters on `inVolume`. It does NOT skip balls that are already in `arm._pending`. The `top` is the highest z.
- `flowerarm.js:121-124`: a `held` ball goes through `world.release`, otherwise state is set to `free` directly. Then `_pending.push` and `fedCount++` run with no check that this ball is already pending.
- `web/js/balls.js:338-341` `release()`: sets state `free`, sets velocity, and does NOT move x/y/z. A just-released ball is therefore still at its old position and still "in volume" until the next physics step.
- `fedCount` has no consumer outside `flowerarm.js` (grep of web/js and web/*.html). Its only effect is the 4-per-deploy budget, so a double release spends that budget.
- `web/js/app.js:1070` passes `count: S_PRACTICE.ammo` (hopper count) and `cap` (99 unless ammoLimit). Released balls are not counted by the app.

## Answers to the questions
1. Released again while still in flight/pending: YES. Nothing excludes an in-flight pending ball from top selection. It is re-picked whenever it is still in the xy bbox (+1.5 in margin) with z >= 0, and it is the highest z. A ball that stays in volume (static, slow, or hitch) is re-released every interval until the 4-per-deploy budget runs out.
2. Counted twice in fedCount: YES. Every re-release increments `fedCount` and pushes a duplicate `_pending` entry.
3. Re-selected as top next tick: YES (case A, and real case in call 2/3). The release does not move the ball, so it is still top in the next feed call.
4. `inVolume` on pending balls: no pending check at all. The z lower bound of 0 (not 4.25) lets floor-resting balls count, which is the path that re-feeds `lo` in the real run.
5. Feeding a ball that was never actually fed: the real run shows `lo` counted as fed 3 times while physically only 2 balls exist. Downstream, the hopper cap (`count + _pending.length`) is over-counted, so the arm can report full early.

## Suggested fix (NOT applied, owner = flowerarm.js)
- In the top loop, skip any `b` with `arm._pending.some(p => p.ball === b)`.
- In the pending filter, drop duplicates (keep first entry per ball).
- Consider `b.z >= scoring_volume_z[0] - b.r` (or `margin`) instead of `b.z >= 0`, so resting balls below the opening are not fed.
- Add a regression test: 2 stacked balls, the balls stay in volume (or are held static), 8 calls, expect `fedCount === 2`, each ball released once.
