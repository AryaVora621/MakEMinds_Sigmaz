## Config parity (diffed by a node probe, executed)

- DEFAULT_FLOWER_CFG vs flower_arm.json: **no numeric drift**. Every shared value matches (hinge, arm, angles, timing, paddle, reach, feed, intakeMouth).
- DEFAULT_ARM_CFG vs flower_arm.json: **no numeric drift** in hinge, arm, angles, timing, paddle.
- DEFAULT_ARM_CFG vs DEFAULT_FLOWER_CFG: only the keys that DEFAULT_ARM_CFG omits by design (`reach`, `feed`).
- Keys present in the json but not in either JS default (metadata or unused): `schema_version`, `name`, `units`, `frame`, `servos`, `cad_todo`, all `*.prov`, and `timing.ease` ("smoothstep"). `ease` is hardcoded in flowerarm.js, so the json value is not read.
- Drift risk: none is enforced by a test. The only guard is the human-edited copies. A parity test (deep-equal of the geometry subset) is the cheap fix.

## Findings

1. **Double feed (real bug, reproduced).** `feedFromFlower` (flowerarm.js ~line 112) picks the highest pollen in the flower volume without excluding balls already in `arm._pending`. A ball released at t=0 is still inside the volume margin and can be re-selected on the next 0.25 s tick. Probe (flower 1, cap 99, 0.05 s steps, 2 s): released ids were `[A, B, C, C]`, so `C` was released twice, `fedCount` reached 4, and only 3 distinct balls were fed. The existing cap test (line 102) only counts `released` and passes, so it misses this. Suggested fix (not applied): skip balls in `_pending`, and add a test that asserts distinct ids.
2. **Parity is untested** (see the parity section above).
3. **buildFlowerArm does not merge defaults.** flowerarm3d.js line 20 uses the cfg as given. A partial cfg throws on missing keys, unlike `FlowerArm`, which merges. Only the full-cfg path is tested.
4. Hopper count includes pending releases (line 110), which is not tested. Pending timeout (1.5 s) is untested, so a stale pending entry cannot be caught.
