## (3) Recommended minimal design (stdlib + numpy)

1. Input dispatch by extension: `.glb`/`.gltf` (JSON chunk + BIN chunk), `.stl`, `.obj`, `.zip` (per-part STL or OBJ inside).
2. STL: check binary vs ASCII by size, not by the `solid` header (see pitfall a). Binary = 80-byte header, uint32 count,
   then 50 bytes per triangle (normal + 3 verts float32 + uint16 attr). Read with `np.frombuffer` with a structured dtype.
   ASCII = parse `vertex x y z` lines, group by 3.
3. OBJ: parse `v` lines, `f` lines (1-based, negative indices allowed, fan-triangulate n-gons), and `o`/`g` lines as part names.
   Ignore `vt`/`vn`/`usemtl` for geometry (optionally keep usemtl as colour key).
4. Units: every source is scaled to metres (glTF's native unit) with an explicit `--units mm|m|in` flag. Default mm for STL/OBJ.
5. Axis: remap to glTF Y-up with a 3x3 (x, y, z) -> (x, z, -y) for a Z-up source, or identity for Y-up. Record the choice in the report.
6. Per part: `mesh_lib.dedupe` on the (3M,3) array (tolerance expressed in metres, e.g. 1e-5 m = 10 um; or scale first).
7. GLB writer (stdlib struct + json): header `glTF`, version 2, total length; JSON chunk padded with spaces to 4 bytes;
   BIN chunk padded with zeros. One buffer, one bufferView + accessor per part for POSITION (float32, with min/max)
   and indices (uint32 to be safe above 65535 verts). One mesh per part, one node per part with `name` = part name,
   one material per part with `pbrMetallicRoughness.baseColorFactor` (colour from the zip member or a default grey).
   Root scene lists all nodes. No extensions, no Draco, no textures, no sparse accessors.
8. Output: `web/data/robot.glb`. The loader defaults are upAxis 'Y', forwardAxis '+X' (MODEL_README.md:34), so
   `--forward` must be recorded and reported. The loader centres and floors the model (MODEL_README.md:37-39), so
   absolute origin is not critical.
9. Verify: re-read the written GLB with a small stdlib check (magic, lengths, accessor counts, bbox in metres) and
   load it in headless Chrome via the existing loader (evidence needed, not done here).

## (4) Pitfalls

a. STL files often start with `solid` even when binary (many exporters do this). Decide by file size:
   `size == 84 + 50 * count`. Unverified against an actual Onshape export (no file in repo).
b. Onshape STL default units: stated in the task as millimetres. Unverified from a source here. Make `--units` explicit.
c. cadlib.M2IN converts metres -> inches (cadlib.py:119). Do NOT reuse it for STL/OBJ, whose units are mm, not metres.
d. MODEL_README says a GLB export from Onshape may be metres or mm and the loader auto-detects (MODEL_README.md:11, :37).
   The output here should be written in metres with an explicit scale so auto-detect is never needed.
e. STL has no node names and no hierarchy. Per-part STLs in a zip: map zip member stem -> node name. Duplicate stems
   across folders must be disambiguated by full path (unverified how Onshape names zip members).
f. OBJ: `o` and `g` both define groups; `o` is the per-object name, `g` sub-groups. Pick one (recommend `o`) and document.
   OBJ indices are 1-based; negative indices count from the end of the current list; `vt`/`vn` shift nothing for `v`.
g. OBJ/STL with multiple bodies per file: `dedupe` merges coincident vertices across bodies. Fine for a visual model,
   wrong only if per-body identity is needed.
h. GLB: accessor `min`/`max` are required for POSITION; JSON chunk must be padded; buffer lengths must be multiples of 4.
i. robotglb.js does not support sparse accessors, Draco, meshopt, or textures (MODEL_README.md:52-54). Keep output plain.
j. Moving parts: loader matches names containing turret/hood/flywheel (MODEL_README.md:43). Keep those words in node names.
k. The GLB spec details above are from general knowledge of glTF 2.0; no URL was fetched in this session. Treat as unverified
   until checked against https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html (not opened here).
