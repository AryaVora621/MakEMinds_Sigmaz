## Where the patterns live
- robotglb.js:201-205 DEFAULT_NAMES = turret:['turret'], hood:['hood'], flywheel:['flywheel','fly wheel','shooter wheel']. Only these three keys. **No intake or flower pattern exists anywhere in code.**
- robot_spec.json and robotspec.js contain no name patterns (no `names` key). Spec has intake (line 36), flower (line 89) but nothing maps them to CAD nodes.
- Patterns are overridable only via `loadRobotGLB(..., {names})` (robotglb.js:215). app.js:251 passes `{}`, so defaults are always used.

## Matching logic (robotglb.js:213-232)
- Case-insensitive substring match (line 215-216). `neighborhood`, `Hoodie`, `Fly Wheel`, `FlyWheel.001` all match.
- Pattern order beats depth: the `break` at line 227 stops at the first pattern that hits. So 'flywheel' wins over 'shooter wheel' even if the latter is shallower.
- Within one pattern, the shallowest node wins (`d < bestDepth`, line 222). Ties go to the first child in traversal order (strict `<`). So `Turret <1>` beats `turret_assembly` if it comes first at the same depth.
- Mesh branch (line 223): a mesh whose name matches uses its parent if the parent also matches. Otherwise it returns the mesh, so the rotation target can be a leaf mesh.
- Depth for a mesh match is recorded at the mesh's depth, not the parent's (minor; can let a deeper non-mesh shadow it).
- Nothing is sanitised. Node names are stored raw (robotglb.js:146: `o.name = n.name || 'node'+i`). Mesh names get `'#k'` appended (line 159). `Turret <1>` stays `Turret <1>`.
- The `missing` list (line 229) is only for turret/hood/flywheel.

## Rotation / pivot (the bigger problem)
- **The found parts are never rotated.** `findMovingParts` output is only consumed by its own test. app.js:251-254 adds the CAD group and hides the procedural robot's children. Turret, hood and flywheel are driven on the procedural `built.turretGroup`, `built.hoodPivot`, `built.flywheelMesh` (app.js:260; robotmodel.js:510 sets `turretGroup.rotation.z`). So with `data/robot.glb` present, the CAD turret/hood/flywheel stay static even though shot logic runs.
- Pivot origin: the node is rotated about its own local origin, as exported. placeCAD (robotglb.js:263) only recentres the outer group, not each node, so a node whose origin is the assembly origin will rotate about the wrong axis. MODEL_README.md:44-47 admits this ("Onshape uses the assembly origin for every node"). Onshape export behaviour is not verified here (no source in repo).
- Turret yaw axis should be vertical (Z in robot frame); no code checks the found node's axis.
- Intake and flower are not discovered at all, so there is no way to animate them from CAD.

## Issues and fixes (file:line)
1. robotglb.js:201-205 / app.js:251-260: CAD parts not wired to animation. Fix: after `tryLoadRobotGLB`, read `r.model.parts.turret/hood/flywheel`, and drive `node.rotation` (or a wrapper group at the true pivot) from `turretDeg`/hood/flywheel state. Hide or stop the procedural pivots when the CAD is used.
2. robotglb.js:202-205: add `intake: ['intake']` and `flower: ['flower']` and a `flower arm` alias, but exclude the spec-listed shooter/intake collision: give intake a `exclude` or use word boundaries. Mark as TODO until the CAD names exist.
3. robotglb.js:215-216: use word-boundary regex by default (e.g. `/\bhood\b/i`, `/\bturret\b/i`, `/\bfly[\s_-]?wheel\b/i`, `/\bshooter[\s_]wheel\b/i`) to stop `neighborhood`/`Hoodie`/`intake_roller_flywheel`. Note `\b` treats `_` as a word char, so `intake_roller_flywheel` still needs an exclude for `intake`.
4. robotglb.js:222-223: prefer the shallowest match and skip nodes whose name contains `static|fixed|housing|bracket|mount` (ASSUMED; no CAD names verified). Document that `static` is an assumption.
5. robotglb.js:146/159: names are not sanitised. Add normalisation (`name.replace(/\s+/g,' ').trim()` and strip the `#k` suffix) before matching, so `Turret_1` and `Turret <1>` compare the same. Consistent with three's `PropertyBinding.sanitizeNodeName` (three.module.js:49721: spaces to `_`, strips `[].:/`), but this loader does NOT call it, so the two conventions differ.
6. robotglb.js:222: depth for the mesh-to-parent case uses mesh depth. Use `d - 1` when returning the parent.
7. MODEL_README.md:44-47: the "rotate via found node" claim is false today (no consumer). Update the doc once fix 1 lands.
