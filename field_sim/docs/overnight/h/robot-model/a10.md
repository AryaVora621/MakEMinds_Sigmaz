## 1. How the arm is modelled
- Logic: `FlowerArm` (web/js/flowerarm.js:22). One scalar drives everything: `progress` in [0,1], eased by `ease()` (smoothstep, flowerarm.js:5). `angleDeg = stowedDeg + (deployedDeg - stowedDeg) * ease(progress)` (flowerarm.js:34-37), so 90 is stowed and -35 is deployed (flower_arm.json:angles).
- State machine: `state` in stowed / deploying / deployed / stowing. Timed by `timing.deployS` and `timing.stowS` (0.45 s each, marked "repo" in provenance). `update(dt)` (flowerarm.js:50-60) moves `progress` and sets `angleDeg`.
- Visual: procedural arm `buildFlowerArm` (flowerarm3d.js:20). Hinge is a child Object3D named `flowerArmHinge`, wrist is `flowerArmWrist`, group is `flowerArm`. `setAngle(deg)` sets `hinge.rotation.y = -deg` and wrist counter-rotates so the paddle hangs (flowerarm3d.js:63-66). `setFraction(f)` and `sync(arm)` are wrappers (flowerarm3d.js:68, 70).
- So the state variable is the scalar `progress` (or equivalently `angleDeg`, which is derived from it). Extension is not used. Phase is only the state label.

## 3. Can a CAD node named "flower" be bound?
Not today. Two gaps.
- Gap A (name list): `DEFAULT_NAMES` (robotglb.js:201-204) has only `turret`, `hood`, `flywheel`. `findMovingParts` (robotglb.js:213-233) iterates `Object.keys(DEFAULT_NAMES)` only, so it never searches for `flower`. Passing `opts.names = {flower: [...]}` through `placeCAD` (robotglb.js:271) is silently ignored because the key is not in DEFAULT_NAMES. The return object has no `flower` field.
- Gap B (no binder): nothing in web/js reads a CAD flower node. The only `flower` strings in the CAD path are the procedural `parts.flower = A.group` (robotmodel.js:394) and the visibility line (app.js:255). Also `tests_js/robotmodel.test.mjs:233-250` covers turret/hood/flywheel only.
- The CAD node is not a free drop-in: its origin and axis are unknown. The logic expects the hinge at robot-frame (8.0, 0, 9.2) in (flower_arm.json:hinge, provenance placeholder), rotation about the lateral y axis, sign -deg, and a paddle tip at `tipRobot()` (flowerarm.js:65-68). A CAD pivot offset or axis mismatch would need a transform. Not measured.

## 4. Interface the CAD binder must call each frame
Intended minimal path (after adding `flower` to DEFAULT_NAMES):
1. `const m = await loadRobotGLB(THREE, 'data/robot.glb', robotSpec, {})` (robotglb.js:281).
2. `const mv = findMovingParts(m.group)` returns `mv.flower` (new key, does not exist yet).
3. Each frame in app.js after line 1072: `cadFlowerNode.rotation.y = -flowerArm.angleDeg * Math.PI / 180` (same sign as flowerarm3d.js:64). Better: add `setAngle`/`sync` to a small wrapper with the CAD node and the pivot offset, then call `wrapper.sync(flowerArm)`.
4. Hide the procedural arm when the CAD node is bound (app.js:255 currently forces it visible). Do not hide it before the binding is confirmed.
5. Read `flowerArm.progress`, `state`, `tipRobot()` for logic. They do not depend on the mesh.

## 5. Gaps summary
- G1: `findMovingParts` has no `flower` key (robotglb.js:201-204). Blocks the bind.
- G2: `opts.names` cannot add new keys (robotglb.js:215 iterates DEFAULT_NAMES only).
- G3: no CAD pivot/axis/origin transform for the flower node. Unknown until measured from the Onshape model.
- G4: app.js:255 keeps the procedural arm visible for every CAD load. A CAD flower would be drawn on top of it.
- G5: the wrist/paddle counter-rotation (flowerarm3d.js:65) assumes the procedural 4-bar. A CAD paddle would need its own hang logic or a fixed pose.
- G6: `tests_js/flowerarm.test.mjs` and `robotmodel` tests do not cover a CAD flower node. Not run in this audit.
