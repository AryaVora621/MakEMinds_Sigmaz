# a05: pivot handling for animated CAD nodes (read-only audit)

Ran: Read of web/js/robotglb.js, web/js/robotmodel.js, web/js/app.js:245-260; Grep for findMovingParts / parts usage under web/. Nothing executed, no CAD file inspected (did not check whether data/robot.glb exists), no edits.

## Answer: no re-pivoting exists for CAD nodes

- robotglb.js:141-165 (parseGLB build): each glTF node becomes a THREE.Group whose position/quaternion/scale come from node.matrix or TRS (147-154). Mesh primitives are attached at identity under that group (159). Vertex data is NOT re-based. So a node's origin is the glTF node origin, not the part's pivot.
- robotglb.js:213-232 (findMovingParts): returns the raw node Object3D (or, for a mesh hit, the mesh itself at 223). No reparenting, no pivot. Pattern match is substring, case-insensitive, topmost wins (221-226).
- robotglb.js:238-273 (placeCAD): wraps the scene in orientG > scaleG > offsetG (240-243) and recentres/floors (262-263). Only the outer transforms change. Node-level transforms are untouched. Returns parts at 271.
- robotglb.js:281-300 (loadRobotGLB): passes straight through to placeCAD. No pivot logic.
- The only hint of the contract is web/data/MODEL_README.md:46: "the node origin should be the pivot". Nothing enforces it.

Consequence: if the Onshape export puts geometry at world position under identity-transform nodes (UNVERIFIED, export not inspected), setting turret.rotation.z would swing the part about the file origin, not the turret axis. Even a correctly-authored node-origin export gives no check.

## Axes (procedural robot is the reference convention)

- Turret: yaw about +z (up). turretGroup.rotation.z = rad(turretDeg) at robotmodel.js:510; pivot at spec pv (414).
- Hood: pitch about the lateral axis y. hoodPivot.rotation.y = -rad(hoodDeg) (511, default at 474). Cheek plates sit at +/-y (471), so y is the lateral axis.
- Flywheel: spin about its own y, which is the axle. Wheel cylinder 'y' (454), shaft 'y' (461), flywheel.rotation.y = flywheelRad (512).
- shooterGeometry (robotmodel.js:23-39) is pure math: exit point = pivot + Rz(turret) * exitPoint (28); no meshes, no rotation of geometry.

## Driver status (important, worse than the pivot issue)

- app.js:251 calls tryLoadRobotGLB(THREE, 'data/robot.glb', robotSpec, {}). Empty opts gives default orientation upAxis 'Y' (robotglb.js:181-182). A Z-up CAD would be mis-oriented unless the caller passes orientation.
- app.js:253 hides every procedural child of the robot group; app.js:254 adds the CAD group.
- app.js:260 and app.js:550 (built.animate in robotmodel.js:550) keep driving the PROCEDURAL turretGroup, hoodPivot, flywheelMesh, which are now invisible.
- r.model.parts is never read (grep: no hit). So CAD turret/hood/flywheel never move, even with a perfect pivot.

## Minimal pivot-fix design

1. Add repivotMovingParts(THREE, model, spec) in robotglb.js, called after placeCAD (after updateMatrixWorld). For each key in order turret -> hood -> flywheel:
   - create Group pg at pivot P, add it under the parent (outer for turret, previous pivot otherwise);
   - pg.attach(node) (Object3D.attach keeps world transform);
   - store pg in model.pivots[key] and the node in model.parts[key].
2. Pivot P and axis per key, using EXISTING spec fields (no new invention):
   - turret: P = spec.shooter.pivot (robot frame; robotmodel.js:398, 414), axis z.
   - hood: P = spec.shooter.hood.pivot (turret-local; robotmodel.js:418, 448), axis y, sign -1 (511).
   - flywheel: P = spec.shooter.exitPoint + [0,0,spec.shooter.flywheelAbove] (turret-local; robotmodel.js:416), axis y, child of hood pivot, offset (fc = fcT - hp, 417).
   The procedural model already uses these, so the CAD pivots match the same kinematics.
3. Driver: when a CAD model is loaded, app.js should drive model.pivots.* (turret.rotation.z, hood.rotation.y = -rad(hoodDeg), flywheel.rotation.y) instead of the hidden procedural groups. Keep one code path with a small adapter. Pass the real orientation in app.js:251 opts.
4. Fallback when the spec pivot is far from the CAD node: pivot = bbox centre of the node projected on the axis (computed from Box3 after updateMatrixWorld). Use only if the check fails, and log it.
