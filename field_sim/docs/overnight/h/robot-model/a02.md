# a02: orientationMatrix and Z-up metre normalisation audit

Ran: read-only Read/sed/Grep only. No tests, no node, no browser. All maths is by hand.
Read: web/js/robotglb.js (1-307), web/data/MODEL_README.md (18-34), web/vendor/three.module.js (Matrix4.set at 5979, winding at 29613). Grepped web/ for callers: none outside robotglb.js and MODEL_README.md.

## Convention (robotglb.js:7, robotmodel.js:2)
Robot frame: +x forward, +y left, z up, inches, floor z=0, chassis bbox centred on x=y=0. Right-handed.

## orientationMatrix (robotglb.js:181-191)
- Matrix4.set is row-major (vendor three.module.js:5979-5984), so rows of m are [f; l; u]. Robot = (f.v, l.v, u.v). Correct.
- left l = u x f (line 185). Then f x l = u, so the basis is right-handed and det(m) = f.(l x u) = +1 for every axis pair. Hand-checked: l x u = f, so det = f.f = 1.
- Consequence: no option can produce det -1. Sign flips from axis choice are impossible. There is no `flip` option. yawDeg (line 189) is premultiplied by a Z rotation, so it stays det +1.
- Parallel check (line 186) uses |u.f| > 0.5. Correct for unit axes.
- Parsing: upAxis 'Z' becomes '+Z' (line 182). forwardAxis 'X' becomes '+X' (line 183). Both work. Default when unset: up +Y, forward +X (so left = -Z).

## Worked example: Z-up, Y-forward file (the case in the task)
Set upAxis 'Z', forwardAxis '+Y'. Then u=(0,0,1), f=(0,1,0), l = u x f = (-1,0,0).
m rows = [f; l; u] = [0 1 0; -1 0 0; 0 0 1]. det = +1.
File point (1,2,3) maps to (f.v, l.v, u.v) = (2, -1, 3). Forward = file y (2), left = -file x (-1), up = file z (3). Correct.
Z-up, X-forward (the header example, upAxis 'Z', forwardAxis '+X') gives m = identity. Correct.
Y-up glTF, forward +Z (upAxis 'Y', forwardAxis '+Z'): l = (1,0,0), m rows [0 0 1; 1 0 0; 0 1 0], det = +1. File (1,2,3) maps to (3,1,2). Correct.
So the Z-up Y-forward case IS supported. Use { upAxis: 'Z', forwardAxis: '+Y' }.

## Winding and handedness
- Because det = +1 from orientationMatrix, triangle winding is preserved and nothing needs flipping.
- The only path to det < 0 is a negative opts.scale. placeCAD (line 258 area, `scaleG.scale.setScalar(scale)`) does not validate sign. three.js then flips frontFace (vendor three.module.js:29613), so faces stay correct but the model is mirrored. Low severity.
- A genuinely mirrored CAD export cannot be corrected: no mirror option exists. Not a bug today; note only.

## Findings
1. Low, robotglb.js:182 and MODEL_README.md:23. Default upAxis is 'Y' but the header example (robotglb.js:9) and the README both say Onshape is often Z-up. If the file is Z-up and the caller passes nothing, the robot lies on its side. The only guard is the >18.5 in warning (line 267), which fires only when a dimension exceeds the limit. Fix: pass upAxis explicitly in the call, or add a warning when the Y extent is much larger than the footprint.
2. Low, robotglb.js:244 and 250 and 264. Box3.setFromObject(outer) is called without precise=true. Three.js then uses the transformed local AABB corners, which overestimate the bounds of rotated child nodes. That moves the centring and the size. Fix: setFromObject(outer, true).
3. Low, robotglb.js:258. Negative opts.scale is not rejected. Gives det < 0 and a mirrored model. Fix: require scale > 0.
4. Unit table (robotglb.js:12): m -> 1/0.0254 = 39.3701 in per m, cm -> 0.3937, mm -> 0.03937, in -> 1. All correct.
