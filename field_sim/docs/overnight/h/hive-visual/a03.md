## Q1: does cellSensors take the current rotation?
- No. hivemesh.js:204 `cellSensors(hive)` takes only {pivot, cells}; there is no angle input. It is built once in the BallWorld constructor, balls.js:232, from hdef.cells.
- hdef.cells is the CAD-pose state (app.js:285 uses states[cad_pose_state].cells, with cadAngle = cad_pose_angle_deg). So the sensors stay in the CAD-local frame for the whole run.
- The tip is applied to the ball, not the sensor: BallWorld._loc (balls.js:692-695) maps world to local with the inverse of delta. delta = (angle - cad) is set in reset (balls.js:274) and updated per substep (balls.js:428-450, 464). _toWorld (balls.js:~735) is the forward map. Both are consistent.
- Recompute is therefore not needed. Hazard: passing a tipped state's cells into cellSensors while delta is still applied would double-rotate. Checked: this gives wrong results for the tipped-state records (naive column below). Current callers all pass CAD cells (app.js:285, tests_js/balls.test.mjs:14, tests_js/physics3d.test.mjs:26).
- Display and aim code (app.js:221, 321, 928) reads state cells directly in world frame, which is correct because it is not rotated again.

## Q2: is a ball through the tipped opening detected by crossesOpening?
Check: segment from 4 in outside the opening aim point to 4 in inside, mapped through the tip delta, tested with crossesOpening (hivemesh.js:238) against the CAD-pose sensor.
- Outside-to-inside crossing: true for all 8 records. Reverse direction: false for all 8.
- Falling ball (world -z, 6 in above to 6 in below the aim point): crossesOpening is true for exactly the UP cell in all 4 states, and false for the DOWN cell. Red audience_up: audience yes, far no. Red far_up: far yes, audience no. Blue audience_up: audience yes, far no. Blue far_up: far yes, audience no.
- Aim point pushed 4 in inside: insideCell (hivemesh.js:232) true for all 8 records.
- My script's first expectation (only the up cell crosses from outside) was wrong for down cells. Its 4 MISMATCH lines are my expectation error, not a code fault. The falling test is the correct physical check, and it passes.

## Findings
1. No orientation bug found. Tip-state cell geometry matches the CAD-pose sensors plus the ball transform for all 4 tip states, both hives.
2. Hazard for future edits: never pass tipped-state cells into cellSensors (or buildFallbackMesh) while the tip delta is still applied in BallWorld. Suggest a test that asserts this.
3. Blue's CAD state is far_up (+30) while red's is audience_up (-30). Code uses per-hive cad angles (app.js:285), so this is handled, but it is easy to get wrong.
