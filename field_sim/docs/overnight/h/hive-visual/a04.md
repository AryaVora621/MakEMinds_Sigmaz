# a04: How balls leave the hive (audit, read-only)

Scope: web/js/balls.js, with cross-references to web/js/app.js and web/js/hivemesh.js. Only read and grepped; no code run, no tests run, no git commands.

## Answer
1. **No release path exists.** balls.js has no code that releases, ejects or drops balls from a cell on tip. The only `release(` in web/js is `flowerarm.js:121` (flower arm, not the hive). Scored balls are never un-scored. Tip just rotates geometry.
2. **Balls in a cell stay in the cell by construction.** `_placeScored` (balls.js:~412-420 region, called at balls.js:465) re-places every `state==='scored'` ball each frame at its cell slot, rotated by the current `hv.delta`. Scored balls are excluded from `list` (balls.js:~494), so they are never simulated. This matches the comment at app.js:286 ("balls stay in the cell that becomes the down cell (manual 10.5)"). That comment is the only in-repo source for the rule. I did not verify manual 10.5 text in this audit. research_manual.md:61-62 confirms only the tip wording (Sec 10.5.1).
3. **Free (unscored) balls inside a cell are not captured.** `_hiveCapture` (balls.js:~757-771) captures a free ball only if it crossed the opening (`b._enter`), or if it is a start-field preload (`b.start`) resting slow inside for `captureRest`=0.15 s. A non-preload ball that sits in a cell stays `free`, so it is still collided by the mesh and falls under gravity. Whether it exits depends only on whether the opening lies at a low point of the new down cell. **Unverified**: I did not check the opening geometry at a tipped pose against scene.json.
4. **Collider rotation.** Yes, per frame. `step()` (balls.js:~450) sets `hv.dPrev`/`hv.delta` per substep, interpolated from `d0` to `d1`. `_loc` (balls.js:692-695) maps world to hive-local with `delta`, and `_toWorld` (balls.js:~735-738) maps back. The mesh is static in hive-local space. `_hiveSweep` (balls.js:716-717) uses `dPrev` for the ball's old position and `delta` for the new one. `_hiveCollide` (balls.js:747-754) does the same with `omega` for the wall velocity term.
5. **Tunnelling risks** (the most important findings):
   - **Snap path (balls.js:434):** if the tip target moves more than 20 deg in one frame, `hv.delta` jumps to `nd` and `omega=0`. `dPrev` is then set equal to `delta` (balls.js:450), so `_hiveSweep` sees no motion. Balls inside a cell can end up on the wrong side of a wall with no sweep correction. Only `_hiveCollide` penetration resolution (balls.js:749-755, 4 iterations) runs after that. Whether a snap is reachable depends on the caller: app.js:1061 steps `hiveDyn` by the real frame `dt`, and the tip is animated over time in `HiveDynamics`, so a snap would need a large `dt` (frame stall) or a jump in `_angles`. Not confirmed by test.
   - **Substep cap:** `n` is raised by `vmax` including `omega*R` (balls.js:436, 441-446 region), so per-substep mesh travel is bounded by `BALL.maxStepTravel`. This should prevent tunnelling for normal tips. Not verified by a test in this audit.
   - **Entering bypass (balls.js:726, 748):** an entering ball skips the mesh sweep correction and `_hiveCollide` for that substep. A ball that is "entering" but actually behind a wall could pass through. The entry test (`_entering`, balls.js:696-707) requires the centre to be inside the opening polygon grown by r, so the risk is limited to balls at the mouth.
   - **Sleeping balls:** sleeping balls skip statics (balls.js:498, 518). They are woken by `_wakeNear` only when the tip changes by more than 0.02 deg (balls.js:434-435) and the ball is within `hv.R` of the pivot. A tip below 0.02 deg per frame keeps sleeping balls asleep inside a rotating mesh. Low risk, but it is a path.
6. **Conflict to decide (not resolved here):** the user request says balls should "drop out of the hive". The repo rule (app.js:286 comment) says balls stay in the down cell. The sim implements the stay rule. These cannot both hold. Decision needed from the lead or user.
