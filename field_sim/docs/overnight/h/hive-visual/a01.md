# a01: Hive tip animation wiring audit (app.js)

Scope: read-only audit. Read docs/OVERNIGHT_RULES.md, web/js/app.js, web/js/hivecycle.js, web/data/scene.json (grep only). Ran: grep/awk/read commands only. Did NOT run the sim, tests, or a headless screenshot, so the visual result is unverified.

## Verdict
No blocking bug found. The rotation math is consistent: pivot, axis, sign and units all match for both hives. Rotation is nonzero during a tip (60 deg total per tip). Remaining items are cosmetic or need a visual check.

## Q1: pivot and axis, red and blue
- Group placed at pivot: app.js:140 `grp.position.set(...g.pivot)`; scene.json hive_red pivot [59.25,72.0,43.95], hive_blue pivot [84.75,72.0,43.95].
- Meshes are converted to pivot-local space: app.js:161 premultiplies translation(-pivot) for every hive instance. Tags are too: app.js:189 and :206 subtract `pv`.
- So the rotation is about the pivot. Good.
- Axis: scene.json `"axis":[1,0,0]` for both hives, and app.js:1062 uses `rotation.x`. Match.
- Frame (`hive_frame`, 115 instances) is parented to 'field' (app.js:149), so it does not rotate. Good.
- Mirroring: the same formula is used for both hives (app.js:1062). Per scene.json, red cad_pose_state=audience_up (cad angle -30) and blue cad_pose_state=far_up (cad angle +30). Start rotation is 0 for both. A red tip to far_up gives +60 deg; a blue tip to audience_up gives -60 deg.
- The x-axis reflection between the two pivots (x=72 mirror) preserves the rotation sense, so opposite signs are not automatically "mirrored" motion. Whether blue's direction is physically right depends on the CAD and is UNVERIFIED. Check with a screenshot at each state.

## Q2: units and sign of angleDeg
- hivecycle.js:101-102: `angleDeg = moving ? theta/DEG : stable[state]`. theta is radians internally (hivecycle.js:89, 203, 209), so angleDeg is degrees. Consistent.
- stable values are degrees: scene.json `stable_angles_deg {audience_up:-30, far_up:30}`, also hivecycle.js:6 header.
- app.js:1062 `rad(h.shown - h.angles[h.cad])`, with `rad` defined at app.js:315. Units match.
- Sign: the convention is the same in the header (hivecycle.js:5-7), in the CAD values, and in the rotation formula. Consistent.

## Q3: could the visible rotation be zero or tiny?
- Per frame: frameBody (app.js:1076) calls simUpdate (app.js:1078) which runs the loop at app.js:1060-1063. No early return sits between 1034 and 1059 that would skip it. Confirmed by reading app.js:1034-1049.
- dt is capped at 0.05 s (app.js:1077). animationDuration = 0.6 s (hivecycle.js:60), so about 12 frames per tip at 60 fps. Fine.
- Rest pose: rotation is 0 at CAD (app.js:142, h.shown = stable[cad]), which is correct.
- Tip trigger: addScoredBall -> _startAnim (hivecycle.js:185-187, 202-205) sets moving=true, so angleDeg follows theta. Natural tip -> onTip -> app.js:441-442 -> updateAimMarks and refreshTipButtons. Wired.
- Manual flip: app.js:517-518 calls setState(next, true) -> _startAnim (hivecycle.js:240). Wired. Restore paths app.js:551, 570, 636 set h.shown directly, but the loop at 1061 overwrites it next frame, so no stale state.
- No path found where the rotation stays at 0 while the hive is moving.

## Findings (ranked)
1. LOW (cosmetic), app.js:518 and app.js:636 (also 442 is fine): updateAimMarks() and refreshTipButtons() run at the START of a tip, so the aim marks and outlines jump to the new up cell while the mesh is still swinging for 0.6 s. Also, hive[a].state is set before the animation, so the HUD says the new state early. Suggested patch: none required; if you want the marks to follow the motion, move the updateAimMarks call into the onTip handler only (app.js:441-443) and remove it from 518 and 636. Check first that the HUD and aim are not needed mid-swing.
2. INFO, app.js:1062: no bug, but add an assertion or test so the axis sign for both hives is locked. Suggested test (new file, not app.js): assert that for red, angle +30 gives rotation.x = +60 deg, and for blue, angle -30 gives rotation.x = -60 deg. Then confirm visually that blue's up cell moves toward the correct side.
3. UNVERIFIED: the physical direction of blue's tip versus the CAD. Needs a headless screenshot at audience_up and far_up for each hive (SwiftShader, scratchpad dir), then compare to the CAD in the link the user gave.
