# a17: ball lifecycle when a ball is scored into a hive

Scope: read-only audit. I ran no tests and changed no code. Only web/js files were read.

## Short answer
A scored ball is NOT removed from physics or rendering. It stays in `world.balls` with `state:'scored'` (balls.js:417). It is skipped by the physics loop, but it is still drawn at its cell slot and follows the hive tip. Nothing in the current code moves a scored ball back to `'free'` on a tip, so a visible drop cannot happen today. Balls leave the world only by recycling a full cell (balls.js:413), by intake, or by reset.

## Data flow (capture to render)
1. Capture. `_hiveCapture` (balls.js:757-770) calls `_capture` when the centre is inside a cell sensor and the ball was entering (`b._enter`) or is a slow start-field ball.
2. `_capture` (balls.js:405-422):
   - picks the lowest free slot `k` in that cell, counting `state==='scored'` balls with the same hive and cell (balls.js:407-408);
   - if the cell is full, removes the oldest scored ball from `this.balls` (balls.js:410-413);
   - sets `state='scored'`, `hive`, `cell`, `_slot`, zeroes velocity, places the ball (balls.js:417-419);
   - queues `[b, hive, cell]` into `_pending` (balls.js:421).
3. Callbacks, end of `step` (balls.js:465-467):
   - `_placeScored` is re-run for every scored ball each step, so it follows `hv.delta` (balls.js:465, 390-393);
   - `recordHiveBall` runs, then `onCapture`.
4. `app.js:433-439` `onCapture` calls `hiveDyn[alliance].addScoredBall(cell, pos, kind)`. This is the HiveDynamics bookkeeping (count, tip threshold). It stores a plain record with no link back to the world ball id (hivecycle.js:179-185).
5. Render. `syncBallMeshes` (app.js:302-312) iterates ALL of `world.balls`, sets `visible = state !== 'held'`, and sets position. Scored balls are therefore visible and placed at their slot.

## Physics exclusion for scored balls
- `_substep` builds its working list only from `state==='free'` balls (balls.js:494-496). Scored balls get no gravity, collision, or sleep logic.
- The statics loop also skips non-free balls (balls.js:516, 533).
- The ball-ball, hive-sweep (balls.js:510) and robot-collision passes use that list or check `state==='free'`.
- Flower feed skips scored balls (flowerarm.js:113).

## Tip behaviour (does a tip re-activate a ball?)
- `HiveDynamics.setState` on a natural tip (hivecycle.js:213-221) only clears the up-cell `counts` flags and, if `p.releaseOnTip` is true, filters its own `this.scored` list. `releaseOnTip` defaults to false (hivecycle.js:59).
- app.js `onTip` (app.js:441-446) only updates hive state, aim marks, a scorer event and a toast. It never calls `world.release` or changes any ball state.
- `world.release` is called only from flowerarm.js:121, and only for `held` balls.
- Net: with default settings, a tip never re-activates a scored ball in the world. The ball keeps `state:'scored'` and keeps rendering in its slot, moving with the hive.
- Mismatch to note: with `releaseOnTip:true` (test-only; tests_js/h_hive-physics_t17.test.mjs:14, hivecycle.test.mjs:145), `HiveDynamics.scored` drops the balls of the lowered cell but the world balls stay `'scored'` and visible. The count and the picture disagree. No existing test checks the world side.

## Where a visual drop could be hooked in
Option A (smallest): in `app.js` `hiveDyn[a].onTip` (app.js:441), when the lowered cell is known, release the world balls of that hive and cell.
- Lowered cell: `state==='far_up' ? 'audience' : 'far'` (mirrors hivecycle.js:217).
- Select: `world.balls.filter(b => b.state==='scored' && b.hive===a && b.cell===lowered)`. Match by hive and cell, because HiveDynamics has no world id.
- Release: `world.release(b, vel)` (balls.js:338-341) sets `state:'free'`, clears hive/cell/_slot, and sets the velocity. `vel` could be the hive's tangential velocity at the ball (`omega x r`), or zero, to make it fall. This is the same path flowerarm uses.
- Caveats:
  - a released ball whose centre sits inside the now-down cell is not re-captured unless it crosses the opening again (`_hiveCapture` only re-captures `_enter` balls or start-field balls, balls.js:762-768). Unverified in motion.
  - `_slotPos` recomputes slots for the remaining balls only when a new capture happens, so the other balls in the cell keep their `_slot` numbers and may leave gaps. Harmless, but not verified.
  - the release must run in the same frame as the tip, or the ball sits at the old angle for a step.
  - the hive's mesh and the released ball may overlap at the start of the fall. `_hiveCollide` pushes it out, which may look like a bounce.

Option B: inside `HiveDynamics.setState` with `releaseOnTip`. This is no good on its own, because it has no access to world balls. It would need a callback that passes the release list.

Option C: a visual-only "drop" that does not touch physics. Animate the mesh of released balls with their own tween, then drop the ball from `world.balls` when the tween ends. This avoids physics risk, but the world and the picture would disagree during the tween. It is not recommended.

## Gaps and unverified points
- No test covers a tip with real world balls. All of `tests_js/h_hive-physics_t17.test.mjs` runs against HiveDynamics only.
- I did not check whether `_hiveCollide` actually lets the scored or released balls move with the hive mesh. Unverified.
- The 8-ball tip threshold and the nectar weight come from the lead facts; I did not re-check them.
