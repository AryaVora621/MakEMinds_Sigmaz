**Verdict:** No stuck balls, no NaN, no wall tunnelling reproduced. Free pollen resting in the up cell at tip time all fall out through the opening (16/16 exits across red and blue, 0 through a wall). Pollen captured through the opening stay in the cell and ride with the hive, so they never drop out. That second behaviour is by design and conflicts with the "balls actually drop out" request. It needs a user decision (see Caveats).

**Classifier notes (honesty):**
- First pass labelled every exit "wall". Cause: `crossesOpening` (web/js/hivemesh.js) only detects entry (outside to inside), so exits need the reversed segment. Fixed in tip_repro.mjs.
- The sensor's opening plane is inset 1 in (OPEN_INSET in hivemesh.js), so the sensor boundary is about 1 in inside the true opening plane. Exit classification therefore tests against the true d=0 plane (sensor P moved by -n). Fixed.

**Caveats and unverified:**
- The "balls drop out" request is not met for captured balls. HiveDynamics (web/js/hivecycle.js header) says tips do not remove balls, and the world keeps scored balls in the hive frame, so they never fall. Free balls do drop out. Whether scored balls should drop on a tip is a user decision, not made here. Options: (a) release scored balls from the down cell on tip, which is what `releaseOnTip` does in the rule model but only for dyn, not the world; (b) keep them.
- The free-scenario pollen were placed by hand inside the cell, not dropped from above into a hive that has already tipped. The drop-into-tipped-hive path was not tested.
- Only the CAD mesh collider was used (no fallback mesh). No 3D or headless-browser screenshot was taken, so the visual result is unverified.
- Read-only on web/ and tests_js/. No git commands run. Only my scratch files and this report were written.
