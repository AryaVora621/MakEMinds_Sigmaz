## Answers to the four questions

1. Snap or animate on external setState(..., true)? ANIMATES. app.js:636 calls hiveDyn[a].setState(name, true) (hivecycle.js:236-240 starts an eased _startAnim, 0.6 s smoothstep, hivecycle.js:60). The visual follows via app.js:1061-1062 (`h.shown = hiveDyn[a].angleDeg`, rotation.x), and balls get the same angle via app.js:451 (world.setHiveAngles). Note: the `setState(name)` (animate=false) path used by resetField/resetHiveDynamics snaps, as intended.

2. Balls resting in cells reassigned correctly? Partly. Cell membership is by physical cell name ('audience'/'far', hivecycle.js:122), which does not change on a flip, so balls stay in their cell (matches the rule comment at hivecycle.js:21). _settleAt (hivecycle.js:207-222) clears `counts` on ALL scored balls, which is correct after a flip (the new up cell starts empty). releaseOnTip is false by default (hivecycle.js:59), so no balls are removed. Not verified: balls.js rendering of captured balls under the rotated hive (balls.js:349 only stores the angle; not traced further).

3. Does the sync fire the tip animation twice (button vs sync)? NO double fire. onTip (the scoring/toast callback) is only called for natural tips (hivecycle.js:214-220). Both tip() (app.js:518) and the sync (app.js:636) call setState(name, true) with natural=false, so neither calls onTip. The only onTip path is the ball-triggered tip (hivecycle.js:185-187). The sync does not toast; tip() toasts once.

4. tip() (app.js:516-519) and refreshTipButtons (app.js:520): consistent for button and keyboard (T/Y, app.js:595). refreshTipButtons is called on every state change path (app.js:442, 518, 552, 572, 616, 636). OK.

## Bugs found (ordered by severity)

BUG 1 (high): the external sync overrides the sim every 80 ms, even when the robot is not linked and even after a natural tip.
- app.js:636 applies j.tip whenever j.tip[a] !== hive[a].state. It does not check `fresh` (app.js:634) and does not edge-trigger.
- Robot publishes its own alliance's tip every publish (SimJson.java:62-68 writes `"tip":{"<alliance>":"<far_up|audience_up>"}`, from Robot.java:237 `st.farCellUp = FAR_CELL_UP`, published at Robot.java:249). The sim never posts tip back (grep: only run_sim.py:13 documents it).
- run_sim.py:50-53 merges with STATE.update, so the last tip value persists in memory forever, even after the robot stops and after a browser reload (run_sim.py:75-77).
- Result A: a natural tip (ball scores, hivecycle.js:185-187) flips hive to audience_up; within ~80 ms the next poll sees robot's far_up and reverts the hive via setState(far_up, true), with no onTip and no tip count. Scoring is effectively undone.
- Result B: pressing T while linked is reverted the same way (the button appears to do nothing).
- Result C: resetField (app.js:548-553) does not clear the server's stale tip, so after Reset the poll re-applies the old tip.
- Robot-side note: Robot.java:328 flips FAR_CELL_UP only on a robot action; the robot's belief does not follow sim-side tips, so the robot is also stale. Owner: TeamCode SimBridge/Robot (not mine to edit).

Suggested patch (app.js, owner: web/js/app.js):
```js
// module scope, near poll():
const tipSeen = { red: null, blue: null };     // last external value applied (edge trigger)
function applyTipState(a, v) {
  hive[a].state = v; hive[a].target = hive[a].angles[v];
  hiveDyn[a].setState(v, true); updateAimMarks(); refreshTipButtons();
}
// inside poll(), replace line 636:
if (j.tip && fresh) for (const a of ['red', 'blue']) {
  const v = j.tip[a];
  if (v && v !== tipSeen[a]) { tipSeen[a] = v; if (v !== hive[a].state) applyTipState(a, v); }
}
// in resetField() (app.js:548): add  tipSeen.red = tipSeen.blue = null;
```
Trade-off: a robot that re-sends the same value after a sim natural tip no longer forces a revert. A robot flip (new value) still applies. The `fresh` gate stops stale values from a dead link.

BUG 2 (medium): tip() during a natural tip animation cancels the tip score.
- app.js:516-518: tip() reads h.state, which is still the pre-tip value while a natural tip is moving (h.state only updates in onTip, app.js:442). So tip() calls hiveDyn.setState(next, true) where next is the SAME target as the in-flight natural tip. hivecycle.js:239 does not early-return because `this.moving` is true, so it calls _startAnim(name, natural=false) (hivecycle.js:240). The natural flag is lost, onTip never fires, scorer.onTip (app.js:443) is skipped, and the "tipped (N balls scored)" toast (app.js:444) is lost.
- Repro: score 8 pollen into the up cell, then press T within 0.6 s.

Suggested patch (app.js:516):
```js
function tip(a) {
  if (hiveDyn[a].moving) return;   // let an in-flight tip (natural or sync) finish so onTip fires
  const h = hive[a], next = h.state === 'far_up' ? 'audience_up' : 'far_up';
  ...rest unchanged
}
```

BUG 3 (low): setState(animate=true) has no guard for same-target-while-moving, and the sync path sets hive[a].state BEFORE calling hiveDyn.setState (app.js:636). This is harmless today (hivecycle.js:239 handles it), but it makes h.state and hiveDyn.state disagree during the 0.6 s move. Any code reading hive[a].state mid-move (app.js:221, 320, 928, 1180) sees the target, not the physical state. Suggest: none required; document it.

BUG 4 (low): hive[a].target (app.js:518, 636) is written but never read. Dead state; no action needed.
