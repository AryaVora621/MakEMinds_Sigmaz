# t01: shotrules.launchBall velocity audit (read-only)

Scope: web/js/shotrules.js (forwardShot, launchBall, speedFromRpm, rpmFromSpeed, solveAuto, evaluateShot), web/js/balls.js (launchScaleFor, BALL_KINDS). Cross-checked against web/js/shot_core.js (lines 1-200) because the solver's sign and unit conventions live there.

What was run: nothing. Read only. No tests, no node, no sim run. Every line reference below comes from reading the files.

## Verified correct (read, not executed)
- Turret sign: forwardShot line 146 uses az = pose.h + turretDeg*RAD (CCW positive). shot_core.js:110 uses turret = wrap(az - psi). Same convention, consistent.
- Hood: el = hoodDeg*RAD (line 146) matches shot_core.js:110 elev = atan2(uz, uhm), launch angle from horizontal.
- Velocity vector (line 151): horizontal = cos(el)*speed along az, vertical = sin(el)*speed. Speed is the shooter-relative exit speed, and the robot/pivot velocity is added after. Matches shot_core.js:24-25 and :199.
- Robot-velocity term (lines 149-150): vs = [vx - om*rfy, vy + om*rfx], with rfx,rfy the pivot offset rotated by heading. Identical to shot_core.js:15 and to the rigid-body formula used in balls.js:689.
- Degree/radian: all conversion sites checked and correct: 146 (RAD), 188-189 (DEG to hood, RAD to theta), 194 (DEG turret), 196 (sol ok), 209 and 259-260 (DEG), 263, 387 (DEG), 400.
- rpm <-> speed (133, 135) is an exact inverse of shot_core.js:173-192 when eff, wheelR and rpmScale are valid. rpmScale 0 is guarded by `|| 1` at 133 and 135.
- Division by zero: none found in shotrules. hn guarded at 170 (`|| 1`). rErr at 389 uses Math.max(sol.rpm, 1). massScale is always > 0 (sqrt of positive masses). landing() at 166-170 reads tg.normal unguarded, but line 169 returns before that access when there is no cross, so there is no crash path.
- Mass scaling applied exactly once on each path: forwardShot line 147 (speed x ms), solveAuto line 193 (rpm = inverse of speed/ms), evaluateShot line 371 (recomputes rpm from sol0.speed only). No double application found.
- Nectar mass 0.041 kg is marked ASSUMED (balls.js:35). The sqrt(m_ref/m) rule is labeled ASSUMED (balls.js:38-41, shot_core.js:184-185). Not hardware validated.

## Findings

1. [MEDIUM] shotrules.js:133 and :135 with shot_core.js:173-181. Shooter eff or wheelR = 0 or undefined.
   - speedFromRpm (133) uses sh.eff raw: eff = 0 gives speed 0 for any rpm, and eff undefined gives NaN.
   - rpmEstimate (shot_core.js:174) does `Rw = Rw || 2; eta = eta || 0.45`, so eff = 0 is silently replaced by 0.45 on the solver side.
   - Result: the auto solver returns an rpm that, in forwardShot, produces zero or NaN exit speed. The ball never leaves, and no error is raised.
   - Fix: validate the shooter config once (eff > 0, wheelR > 0, rpmScale > 0; throw or warn). Use the same defaults in both places, or drop the defaults in core.

2. [MEDIUM] shotrules.js:74-122 (flight) and :151 vs balls.js:501 (drag).
   - The solver (shot_core.js is drag-free by its header) and the shotrules flight predictor are both drag-free.
   - BallWorld applies quadratic drag, dragK = 0.0004 (balls.js:63), on every airborne ball each substep (balls.js:500-503).
   - So the aim solution and the "Ball would enter the opening" prediction ignore drag the sim applies. Expect short shots, and the predictor can disagree with the world.
   - balls.js:59-62 says dragK was tuned to the project tests, not measured. The mismatch is a real model gap, not a sign error.
   - Fix: add the same drag term to flight(), or compensate speed. Measure miss distance with the sim and record it.

3. [LOW] shotrules.js:133 has no clamp. shot_core.js:181 has max(0, rpm). A negative ctx.rpm gives a negative speed, and the ball goes backwards. Fix: clamp rpm >= 0 in speedFromRpm.

4. [LOW] shotrules.js:371 mutates the caller's object. `sol0 = ctx.sol` (line 367), then sol0.rpm and sol0.turretDeg and sol0.fromBehind are written. Result is idempotent, but the caller's solution changes silently. Fix: shallow-copy sol0 before writing.

5. [LOW] shotrules.js:203 rangeKey and :206 stationaryOk.
   - rangeKey omits sh.pivotX and sh.pivotY, but the pivot enters the stationary solve (pivotWorld at 137-140). A pivot change returns stale cached ranges.
   - stationaryOk hard-codes normal [-1, 0, 0] (line 206), so the range estimate assumes every opening faces -x. The real ctx.target.normal is ignored.
   - Fix: add pivotX, pivotY to the key, and pass the real normal (or key on it).

6. [LOW, doc] balls.js:29 says mass is "informational only: the physics is not mass-dependent". balls.js:43-46 (launchScaleFor) makes launch speed mass-dependent. Fix the comment.

7. [INFO] Duplicate implementation. shot_core.js:179-199 already has speedFromRpm, rpmForSpeed and launchVelocity. shotrules.js:133-135 and :143-153 re-implement them. Drift risk, which is what #1 is an instance of. Fix: import from Core.

## Not verified (no code run, no other files read)
- app.js: that the turret is drawn as heading + turret, and that the robot velocity passed in is in in/s and rad/s.
- That shooter.eff, wheelR, rpmScale and hood limits are always set in the real config (see #1).
- That callers pass ctx.robotVel when moving (otherwise pose.vx/vy/om is used).
